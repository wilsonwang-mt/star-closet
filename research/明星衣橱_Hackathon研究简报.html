明星衣橱
从电影感，走到可购物。

01 / DECISION

先做一个能被相信的衣橱

用电影式动线讲人物品味，用少量高质量单品证明交互。2–3 天的胜负手，是完整而可信的浏览闭环。

建议 MVP：一个虚构、风格化的奢华衣橱；一条导演式镜头路径；3–5 个可点选单品；其中至少 1 件提供真正的 3D 旋转。

没有背面素材的衣服明确提供图片放大，不把图片翻转称为真实背面。点击购物链接跳转品牌或零售商原始页面，不在演示中处理支付。

进入空间镜头导览选中单品放大 / 查看细节去官方商品页

本报告是研发决策与验证计划，不是已实现的产品。范围与时间均为建议；尚未建立代码仓库、配置跨设备环境或部署演示。

02 / VERIFIED LANDSCAPE

相近产品已存在，组合仍有空间

“明星衣橱”“创作者导购”“可购物 3D 空间”各自已有先例。差异化应落在人物策展 + 单品故事 + 可信细节 + 直接购买入口，而不是只证明房间可以做成 3D。

核验口径：2026-10-12 查阅官方页面、开发者介绍与官方公告。未登录或完整实测各产品交互与结账；当前网页存在不等于所有体验都正常运行。

03 / TWO VIABLE STACKS

代码主导，默认选 R3F

如果主要让 Codex 编写实现，建议 React + React Three Fiber（R3F）+ Three.js。若你已经熟悉 Spline，且接受它的托管嵌入与账号导出条件，Spline 可以更快调出空间构图。

推荐 / 代码主导

React + R3F + Three.js

  • 一个 Canvas 管理房间、灯光和选中状态。
  • Drei CameraControls 驱动入口、总览、特写三种镜头。
  • GLTFLoader 加载服装；普通 HTML 放详情与购买按钮。
  • 已有 Next.js 工程可沿用；新建演示不必为 3D 专门引入 Next.js。

代价：布景与镜头主要靠参数调整，需要投入时间做视觉打磨。

CameraControls · GLTFLoader · R3F 性能指导
有经验时选 / 可视化编辑

Spline + React 网页层

  • 用 Spline 制作房间、材质与预设镜头。
  • Switch Camera 支持时长和曲线，适合导演式切镜。
  • 商品数据、详情和外链保持在 HTML 层。
  • 先验证对象点击到网页 UI 的桥接，再制作完整场景。

代价：账号权益与导出方式影响交付，不能假定任何格式都保留事件与动画。

镜头切换 · 导入格式
Spline 的交付限制必须先检查。

本次查看的价格页将 Code & Self-hosted exports 列于 Enterprise；免费 Web 导出带水印。官方代码导出文档说明动画与事件只在 Vanilla JS / React 导出中启用。不要承诺“免费编辑 → R3F 导出 → 完整自托管且交互原样保留”。实际账号权益与所选导出应当场验证。

当前价格页 · 自托管说明 · 代码导出说明

实现结构：房间负责体验，商品数据负责事实

每个商品保存 id、名称、展示类型、预览图、可选 GLB / 背面图 / 旋转序列、购买链接、人物与商品关系、素材来源和授权记录。镜头转换时禁用冲突拖动；转换结束才允许检查单品。提供重置、返回、普通列表与减少动效选项。

起始工程预算可设主角模型 3–5 MB、DPR 1–1.5，随后用目标设备实测调整；它们是建议，不是性能保证。按需渲染、复用资源、延迟加载，优先于昂贵的景深、体积光和实时反射。

兜底方案：静态房间 + 热点 + 单品 3D 查看器

如果多物体 3D 房间整合失控，可用静态房间图做入口，热点打开 model-viewer。它适合单个模型旋转、缩放和镜头控制，但不自动实现完整衣橱交互。

04 / ASSET REALITY

真正的瓶颈，是衣服资产

能转动的三维服装，需要可用网格、UV、材质、纹理与合理的背面。单张正面商品图不提供这些事实；自动生成可以做概念素材，但不能承诺还原真实商品。

A / 优先

已有授权 GLB / glTF

先导入一件，检查正反面、尺度、面数、透明材质和纹理。模型合格，再扩展单品数量。

来源优先级：品牌提供 → 自制 → 许可明确的素材。购买素材不自动意味着可用于品牌或明星背书。

B / 诚实降级

多角度照片或 2D 展示

有连续实拍角度，可做图片序列旋转；只有正反两张，可做明确标记的正反切换；只有正面，则仅放大细节。

“多角度图片”与“真 3D”分别标记。CSS 镜像并不是商品背面，不能替代缺失资料。

第一天先设止损点：如果一件合格服装模型仍无法在目标设备顺畅展示，就冻结“全衣橱真 3D”的目标，保留 3D 空间 + 2D 商品卡的混合方案。
05 / BUILD PLAN

2–3 天，把闭环跑通

DAY 1

资产与技术可行性

最初两小时确认一件可用模型；若选 Spline，同时验证导出权限与点击桥接。确认授权边界；整理 3–5 件商品和真实链接；在一个简化房间里导入一件模型，完成热点选择、镜头靠近与返回。当天决定真 3D 数量和降级方案。

交付物：最小技术样片、素材清单、选定技术栈。先证明资产能用，再做装饰。

DAY 2

完成演示主线

搭建入口 → 全景 → 单品 → 详情 → 外链的完整路径。加入灯光与材质层次、平滑镜头、加载状态、返回按钮、错误提示和手机布局。

交付物：可重复演示版本。先做完成度，再添加额外衣服。

DAY 3

减负、校验与讲述

压缩模型与贴图，在实际笔记本和手机验收；修复加载与触控问题；录一份演示备份；准备三分钟讲述：为什么这个空间可信、什么是可购物、下一步需要哪些授权和资产。

只有两天时：缩至 3 件商品、1 个房间、1 条镜头路径，取消自由漫游、账号系统与 AI 生成管线。

06 / DEFINITION OF DONE

验收时看什么

维度可检查的结果
叙事与镜头首次进入有明确焦点；每次点击只触发一条镜头动作；可跳过导览、退出详情并回到原位。
商品准确性每件商品具备名称、品牌、素材类型及来源记录；外链指向对应商品或明确说明的品牌页；不虚构库存与价格。
交互真实性真 3D 单品可旋转观察正背面；图片方案按实标记。触控和鼠标均可选中，不依赖悬停。
性能与失败处理在约定设备与网络上记录首屏、可交互时间和帧率；建议以交互阶段尽量稳定 30 fps 为初始目标，未实测不宣称达标。加载失败可退回图片，不留黑屏。
隐私与授权空间为虚构设计；不展示真实住所布局、地址或定位元数据。若使用真人身份、肖像、品牌资产，先确认授权或改成原创人物。
可复现另一台设备按 README 能安装并启动；锁定依赖；演示链接、素材许可与已知限制有记录。
07 / TWO-DEVICE WORKFLOW

跨设备靠同一仓库，不靠复制文件

建议用同一个私有 Git 仓库连接笔记本与另一台开发机器；以下是待执行流程，当前没有替你建立仓库、安装软件或配置访问权限。

首次建立

  1. 由你选择仓库服务和可访问成员。
  2. 提交源码、依赖锁文件、README、PROJECT_BRIEF.md、DECISIONS.md、NEXT_STEPS.md 与 .env.example；排除密钥、node_modules 和构建产物。
  3. 两台机器分别 clone，使用同一 Node 主版本和项目指定包管理器。
  4. 大体积模型采用经确认的 Git LFS 或资产存储方案；不默认上传未获授权素材。

每次换机器

  1. 离开前：确认改动 → 测试 → commit → push。
  2. 到另一台：先检查本地改动，再 pull；按锁文件安装依赖并启动。
  3. 同一时刻只在一台机器编辑同一工作分支；并行工作使用独立分支与合并审查。
  4. 发现冲突先比较内容；不使用强推覆盖另一台未合并的工作。

仓库是源码与项目文档的唯一事实来源。PROJECT_BRIEF 记录目标和范围，DECISIONS 记录已选方案及理由，NEXT_STEPS 记录当前状态与下一步；换设备前一并更新。Git 同步代码与被追踪的资产，不同步聊天历史、登录状态、进程、未提交文件或本地环境变量。若选择 Next.js，还需要可用的 Node 运行环境；它与本 HTML 报告的双击离线阅读是两件事。

08 / OPEN QUESTIONS

现在仍需确认的 5 件事

  1. 对标来源：“老高与小茉”具体是哪支视频、哪个片段或链接？目前不能把它当成已核验产品案例。
  2. 人物与授权：有授权明星还是原创风格人物？演示中能使用哪些名字、肖像、服装图片与品牌标识？
  3. 现有资产：已经有 GLB、服装工程文件、多角度照片，还是仅有商品正面图？这是技术路线的主要分岔。
  4. 演示条件：最终在什么笔记本、浏览器和网络环境演示？是否要求手机可用？是否允许联网加载？
  5. 团队能力：熟悉 React / Three.js，还是更熟悉视觉场景编辑器？谁负责空间与服装资产，谁负责交互？
范围保护：本次建议不包含真实住所复刻、换装模拟、布料物理、购物车结算、明星后台和规模化资产生产。若其中任何一项是比赛硬性要求，需要重新估算工期。
