## 1. 四类交易、四个管理账本

| 账本 | 付款方与购买对象 | 主要交付 | 结算及售后重点 |
|---|---|---|---|
| B2B 入驻服务 | 品牌、机构或创作者团队购买建橱等约定服务 | 采集、草稿、模型、发布或运营包 | 范围、里程碑、验收、返工、退款与伙伴费用 |
| C2B 数字门票 | 粉丝购买指定创作者的授权数字内容访问 | 指定内容、受众范围和期限 | 支付后授权、撤下、退款、创作者应付 |
| C端私密衣橱服务（一次/周期待定） | 用户购买仅本人查看的空间或工具 | 实际具备的容量、保存或配额 | 服务期、退款、导出与删除；周期方案另定义续费取消 |
| 商品成交归因分成 | 消费者购买商品，商家按有效归因交易支付佣金 | 订单、发货、退货和有效归因 | 退款后净成交、佣金池、创作者与平台分配 |

四个账本是管理子账，分别有合同、商品或权益、付款、退款和应付记录。
GMV、代收款、佣金池、创作者应付、平台经济留存及实际利润不能相加。
法定收入采用总额还是净额，应随真实合同主体、责任与适用会计口径核定。
商品平台份额和创作者份额来自同一佣金池，不分别按全额再向商家收费。

## 2. 责任与候选商业路线

先明确合同卖方、收款主体、履约方、内容提供者、退货接收方和客服责任。
前台统一不等于所有商品由同一主体销售或同时送达。
商品页可访问、有价格、能抓取或已有联盟链接，都不构成供货和代收款授权。

| 商品路线 | 成交与履约 | 付款 | 必备条件 | 当前状态 |
|---|---|---|---|---|
| 外链导购 | 零售商成交及售后 | 外站 | 展示和导购授权、有效归因约定 | 比较或明确标识的替代，非唯一既定路线 |
| 授权多商家平台 | 各商家与平台按合同承担责任 | 可在本站，需核实 | 商家资格、报价、订单、支付和售后接入 | 重点评估 |
| 平台销售、合作供货或代发 | 平台承担相应销售责任 | 本站 | 合法供货、资金及履约售后能力 | 候选，未选定 |
| 自营库存 | 平台采购、销售及组织履约 | 本站 | 采购、库存、仓配和资金 | 不建议作为未验证起点 |

供给开放给五类衣橱，不意味着每位创作者都成为商品卖方。
创作者可提供策展与归因，商家可销售和发货；两者身份、费用和责任分别披露。
合作方代发不自动免除平台责任，技术名称不能代替合同。
支付服务商的分账或账户体系不自动解决税务、退款和销售资格。

## 3. 推荐首个试点与退出条件

以下为建议，不是首版承诺，不必同时开放四类收费。

| 试点 | 推荐范围 | 退出条件 |
|---|---|---|
| B2B 建橱 | 一个明确主题、有限内容、明确交付包 | 实际验收、成本可核对、返工与退款有处理 |
| 商品交易 | 单市场、单币种、一家授权供应商、少量 SKU | 报价至履约、退款与佣金对账闭环 |
| 数字门票 | 有正式授权的一组已就绪内容 | 范围可理解、访问可验证、撤下退款可执行 |
| 个人私密服务 | 付费方式未定的有限权益 | 容量、隐私、导出与服务成本成立；周期方案另验续费取消 |

顺序建议为供给与责任 → 体验演示 → 有限真实试点 → 多供应商或更多收费。
尚无真实能力时不收款；使用沙盒只能证明测试流程，不证明真实交付。
失败场景、人工处理和财务对账未闭环前，不扩大人数、商品与收费范围。
市场、价格、阈值、返佣窗口、账期和参与者仍待用户决定及合作核实。

## 4. 身份、访客与信息最小化

建议公共浏览与基础检索不要求注册，语音可回退为文字。
试衣间临时选品可匿名保存，但须说明本机、跨设备及保留期限。
长期个人空间、照片、化身、付费服务和私密权益需要可靠身份与归属控制。
不为转化强制开放照片、公开衣橱或订阅营销。

商品可优先评估访客结算，仅收集支付、通知和履约必要资料。
私密内容访问和个人付费服务必须能安全绑定购买者；是否允许访客购票及如何找回待定。
订单访问不能只凭猜测编号，账号合并需验证归属。
语音录音、身体图像、住址和支付记录不互相默认授权，供应商只获履约必需资料。
用户照片与化身不默认用于公开陈列、创作者广告、训练或合作伙伴素材。
未成年人、冒用他人形象和删除请求需要上线前明确规则；团队代理仅适用公共创作者工作台。

## 5. 商品身份、SKU 与唯一件

| 对象 | 要求 |
|---|---|
| 展示单品 | 有来源、关系与资产范围，不必然可售 |
| 普通 SKU | 对应品牌、颜色、尺码和真实可售规格 |
| 唯一二手件 | 独立实物编号、所有权或寄售依据、成色缺陷与单件库存 |
| 人物原物 | 核实本人关系和销售权限，不从空间推断 |
| 同款、推荐、相似 | 分别标识，不静默替换原件 |

所有核心旋转服饰需要完整真实模型；图片与试穿结果不等于商品模型或实物事实。
化身效果不保证尺寸合身，也不能推导不存在的可售背面。

唯一件需要真实可执行的占用与释放；本地锁不等于供应方已预留。
加入试衣间、收藏、点赞或试穿不代表预留、报价锁定或购买成功。
替换商品、颜色或尺码须由用户重新选择确认。

## 6. 试衣间到报价与购物袋

F11 可以保存来自多衣橱的商品、规格、组合、来源及试穿记录。
试衣间中的展示项、自有衣物、缺货项、可售项及付费内容分开。
门票和个人私密服务不是服装 SKU，也不与实体商品共用退货规则。
建议首轮商品、门票和个人私密服务分别结算与出具明确凭证，统一订单中心可分组查看。

进入商品结算前，按规格、数量、地址与配送方式重算价格和可售状态。
最终报价包含商品、优惠、运费、可确定税费、总额、币种与有效期。
参考价、上次同步价和最终报价分开，变化需用户确认。
无法计算完整应付金额或确认配送地区时，不开启实际付款。
订单保留当时商品、费用、政策和责任快照，不被目录更新覆盖。

## 7. 商品拆单、配送与售后

订单组、供应商子订单、商品行、包裹、售后和退款独立关联。
一个购物袋可能多卖方、多次付款、多包裹和不同退货地址。
确认页说明各方身份、分项运费、预计时效、税费、政策及免邮口径。
跨境须有明确责任，不把未知税费隐藏为保证到手价。

多供应商需先决定组合全成或允许部分成交，以及何种变化再次确认。
候选默认是先尽量核实可售和报价，再按用户确认的部分失败规则执行。
付款后拒单不自动换货或默认为全单成功，需说明应退金额和处理状态。
取消需供应商实际确认；生成运单不等于已揽收。
退货资格、期限、成色条件、运费责任、换货、丢件与错发均需可执行政策。
部分退款按商品、优惠、税费和运费分配，退款发起不等于到账。
客服统一入口，后台定位实际责任人，不让用户在平台和商家间自行猜测。

## 8. B2B 入驻与合作伙伴交付

每个入驻方案明确是资格审核、建橱项目、托管维护还是组合服务。
收入驻费不是保准入、保证流量、保证成交或永久免费服务的承诺。
A 方案按明确制作或维护服务收费，不自动附加成交佣金；B 方案免入驻费后按有效净成交分池。
如另议混合收费，需分别说明服务、佣金、抵扣、退款与总成本，并事前同意。
广告、制作、维护和佣金分别标价及描述，不用一个“入驻费”掩盖持续费用。

合同至少明确素材数量和质量、Agent／人工范围、真模型数量、修改轮次、里程碑、验收人、发布范围、维护、退出和退款。
拍摄、建模、数字形象及履约伙伴需有交付标准、数据用途、返工、费用与撤回责任。
对方提供照片不自动授权所有人物肖像、秀场音乐、模特、品牌和商品模型。
平台验收的草稿不等于商家确认的商品事实，角色和版本分别留痕。
团队代理操作设置所有者、编辑、审核和财务权限，不共享所有者凭据。

## 9. 数字门票与受控内容 F14

购买前展示内容提供方、内容清单或范围、有效期、次数／设备限制、更新承诺及退款办法。
小额价格并不免除授权、交付与客服；具体价格未定。
“私密内容”指受控的授权策展、讲解或独家素材，不出售真实住址、住宅地图或未经同意的生活信息。
取得访问权不自动取得下载、再分发、训练或商业使用权。
访问控制不能保证杜绝截图与复制，平台不承诺绝对防泄露。

权益记录至少绑定购买者、内容／集合版本、访问范围、开始与截止、状态、来源订单和政策版本。
支付成功并核实后再授予；重复回调不重复授予，退款按规则撤回或调整访问。
创作者下架、授权到期、侵权投诉、内容缺失和更新未履行分别有处理。
不可因内容已打开就一概拒绝退款，需符合经营市场与支付平台实际要求。
停止新售、既有用户通知、替代或退款与创作者应付冲回均需可追踪。
移除危险或侵权内容可优先止损，但不得因此省略购买者服务与财务处理。

## 10. 个人私密衣橱服务 F13／F14（一次/周期待定）

点赞收藏达到资格或容量阈值后，可选择付费空间；阈值指标、数值和免费边界未定。
达阈值不自动扣款、不公开原私密资料，也不把互动数兑换为可提现收益。
确认页明确一次解锁或周期候选的服务期、容量、AI 次数或算力额度、到期与超额规则。
一次付款不默认永久无限；“一键试穿”也不意味着付费后可无限生成或保证结果，实际能力与成本另行验证。
自动续费如采用，需清楚选择、通知、取消和价格变更规则，不能默认把试用变为付费。

若采用周期方案，取消续费、即时退款、降级与删除是不同操作，分别展示后果。
到期后如何只读、保留、导出和最终删除须预先说明，不能因超限突然丢失资料。
免费内容、个人付费服务包含权益和另售门票分别标注，避免同一权益重复收费。
个人私密空间仅本人查看，不提供邀请、分享或团队访问；个人公共衣橱另走独立提交与审核流程。
个人照片删除对原图、衍生化身、缓存、合作方副本及备份的范围与时限需定义。

## 11. 商品归因与佣金池 F15

在接入前约定有效触点、归因窗口 W、成交时间、市场、退款和多触点规则。
浏览、点赞、收藏、试穿、加入试衣间及曝光不是已成交佣金。
首轮可评估最后有效点击归因，但规则应在活动前确认，不按结算结果临时修改。
跨设备仅使用获准、可验证的关联方式，不能为补齐归因默认追踪个人私密内容。

一个有效订单只形成一次符合合同的佣金池，多个创作者按规则分配同一池。
商品退货、取消、拒付和无效归因先调整可分佣净额，再形成平台与创作者应付。
商品优惠、运费、税费是否进入佣金基数及扣减口径需书面约定，不按付款总额默认抽佣。
不把商家总佣金、创作者份额与平台份额相加为平台收入。
归因记录保留触点、政策版本、订单行、有效金额、退款、证据和争议状态。
窗口结束、可退期和支付方最终状态如何影响冻结／可结算金额，由合同确定。
已结算后退款需可追踪冲回、抵扣或追偿，不通过删除旧记录处理。

广告项目费与成交佣金只有合同允许、分别交付时可叠加。
赞助曝光不自动拥有商品成交归因，广告来源也不自动升级人物关系。
商家报告展示广告费与佣金总成本；消费者侧清楚标识赞助和利益相关推荐。

## 12. 支付、账单与平台规则

实体商品、数字内容和订阅按真实渠道、市场及支付服务商能力设计。
网站与移动应用的数字内容、订阅、外部付款和链接规则可能不同，上线前核实当前官方条件。
不预先假定能统一外部支付、自动分账或用跳转规避平台要求。
谁承担支付费、税费、拒付、退款和汇兑损失须明确，不能在多方重复扣费。
票务和佣金的创作者收款资格、验证、账期及暂缓支付按真实服务条件落实。

平台代收总额不是平台可自由支配收益；需要区分客户款、合作方应付和平台费用。
不同账本关联同一支付也需分项，不能同笔资金重复确认收入。
支付或分账资格未成立时不真实收款，不能靠手工转账掩盖未解决责任。

## 13. 幂等、状态与失败补偿

下单、支付、供应请求、权益发放、退款及结算分别有稳定标识和幂等机制。
验签回调、持久记录、去重、乱序处理和外部查询均需可恢复。
浏览器返回、界面成功动画与模型生成完成都不是付款或权益交付的唯一依据。

| 异常 | 用户状态 | 必要补偿 |
|---|---|---|
| 支付未知或响应丢失 | 正在确认，可查原记录 | 查既有尝试，避免再次扣款 |
| 已付但供应拒单 | 商品受影响、退款处理中 | 按规则退款、冲回对应归因佣金 |
| 供应已接单但接口超时 | 订单确认中 | 按关联号查询，不盲目重下 |
| 付费内容未开通 | 权益待确认，有求助入口 | 幂等补发或退款，保护其他权益 |
| 重复票务回调 | 显示一次有效购买 | 不叠加次数或重复创作者应付 |
| 周期订阅候选退款或拒付 | 政策对应的权益状态 | 撤销或调整、账本冲回并通知 |
| 内容撤下或授权失效 | 停售及用户说明 | 访问处理、退款或替代、应付调整 |
| 多供应部分失败 | 分开成功与失败 | 依确认规则继续、取消与部分退款 |

订单、支付、履约、权益、退款、归因和结算独立状态，不能互相代替。
例如付款成功可伴随供应待确认；票已退款应伴随对应访问调整和应付冲回。
异常有负责人、时限和人工队列，不以无限重试替代客服与资金处理。

## 14. 对账、风险与隐私

逐项核对商品净额、票款、订阅周期、B2B 交付、退款、支付费、创作者应付及伙伴费用。
保留原始记录与调整分录，不覆盖数字来制造一致。
平台服务留存、创作者收益和商家营销成本从同一资金流核对，单位经济见商业运营文档。
作弊流量、自购返佣、刷赞、假退款、盗用内容与结算账户异常进入调查，避免只靠曝光排名。
对申诉、冻结和恢复有依据与人工渠道，不把算法标记直接当永久定罪。
公开目录、私密身体资料、订单及伙伴结算分别授权，敏感数据不写仓库或公共日志。

## 15. 候选验收与决策门槛

| 场景 | 验收要求 |
|---|---|
| 试衣间转购买 | 商品身份、规格、价格与来源一致，失效项明确 |
| 唯一件竞争 | 不重复成交，占用失效正确释放 |
| 支付及回调重试 | 不重复订单、扣款、权益或应付 |
| 退款后佣金 | 净成交、平台与创作者应付同步调整 |
| 多触点 | 单订单不重复建池，分配合计不超池 |
| B2B 项目返工 | 验收人、版本、里程碑与费用可查 |
| 数字内容撤下 | 停售、访问、用户服务与财务闭环 |
| 周期订阅候选到期 | 续费取消、降级、数据处理和通知符合说明 |
| 权益隔离 | 个人私密、粉丝内容与团队权限不串用 |
| 平台支付限制 | 对应市场和渠道的真实条件有核查依据 |
| 对账 | 四账本独立，代收与收入不重复，差额有人处理 |
| 演示 | 不收真实卡号，不承诺虚构库存、订单、3D 精度或权益 |

未执行的场景保持待验证；静态材料、沙盒、真实供应和真实权益分别验收。
建议先确认首个经营账本、市场、合作责任和最小交付，再决定应用实施范围。
