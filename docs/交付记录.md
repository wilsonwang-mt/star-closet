## 比赛版应用 · better-auth 会话 cookie 缓存：登录校验提速 · 2026-10-17（UTC+8）

依据：协调会话转达 D62 试穿在 Supabase 上的实测——慢链路上每个已登录请求要额外花约 0.64 s 做 better-auth 的 session 校验；任务是评估并开启 `session.cookieCache`，给出前后数字并写清安全取舍。分支 `claude/angry-khayyam-881925`（基于 origin/main `ad7a4a5`）。这是实现层调整，不改产品行为与授权边界，不新增决策编号（D64 已被部署授权占用，D65 为试穿提速）。

### 改动与 maxAge 的取舍

- `app/lib/auth.ts`：`betterAuth({ … })` 增加 `session: { cookieCache: { enabled: true, maxAge: 300 } }`。`app/README.md` 账号一条补了一句说明。
- **建议并采用 `maxAge: 300`（5 分钟，也是 better-auth 默认值）**：试穿的轮询每 1–2 s 一次，一轮试穿持续数十秒，5 分钟内的请求全部命中缓存，之后每 5 分钟只回库校验一次（约多花 0.6 s），体感无差；再拉长只是把撤销延迟变得更大、收益增加很小。本站没有改密、注销账号、“退出所有设备”、封禁这些会撤销会话的入口，撤销只来自“退出登录”，所以不需要更短的窗口。不启用 `refreshCache`（better-auth 在配置了数据库时会自己关掉它）。
- 机制（据 better-auth 1.7.10 源码 `api/routes/session.mjs`、`cookies/index.mjs`）：注册、登录和每次查库的 getSession 响应都会下发 `better-auth.session_data`（HttpOnly、SameSite=Lax、Max-Age=300；默认 `compact` 策略，用 `BETTER_AUTH_SECRET` 做 HMAC-SHA256 签名）。之后的请求带着它：验签、核对其中的会话 token 与 `session_token` cookie 一致、未过期，就直接返回，不查库；缺失、签名不对或过期才回落查库，Route Handler 里经 `nextCookies()` 重新下发，Server Component 里不能写 cookie，源码对这个异常是吞掉的（见下方实测）。

### 安全取舍（要知道的代价）

1. **撤销延迟最多 5 分钟**：会话在服务端被撤销或删除后，仍持有 `session_data`（连同 `session_token`）的客户端，在缓存有效期内仍被当作已登录。实测：删掉 session 行后，带完整旧 cookie 的请求仍通过（改前立即 401）；只带 `session_token` 的请求立即 401；`get-session?disableCookieCache=true` 查库为准，返回 null。
2. **同浏览器退出登录立即失效**（`sign-out` 同时清 `session_token` 与 `session_data`）。但退出前被复制走的整套旧 cookie，在 5 分钟内重放仍有效（实测改后仍通过，改前 401）。拿到整套 cookie 的人在用户退出之前本来就能以本人身份访问，新增的只是“退出或服务端撤销之后”最多 5 分钟的延迟。
3. **D47 不变**：私有照片与形象文件仍由服务端校验登录会话后按本人前缀读取，其他用户、主理人、品牌与运营没有访问入口；变的只是会话撤销最长晚 5 分钟生效。`session_data` 是签名、不是加密：载荷含 session（id、token、userId、expiresAt、ipAddress、userAgent）与 user（id、name、email、emailVerified、image）字段，约 0.9 KB，HttpOnly，页面脚本读不到；`user` 表没有额外字段，不含身体数据、照片或档案。需要加密时改 `strategy: "jwe"`。
4. **以后若增加改密、封禁、退出所有设备**：缩短 `maxAge`，对敏感操作传 `disableCookieCache`，或设 `cookieCache.version` 一次性作废全部已下发的缓存。现在没有需要这些的路由，没有预先加。

### D64 部署核对

写这一节时 `lib/auth.ts` 还没有设 `baseURL` 和 `trustedOrigins`。之后 D64 的部署前 A 档修复（PR #9）加了 `baseURL`、`trustedOrigins` 与 `advanced.useSecureCookies`。2026-10-22 把 main 合进本分支时核对：cookie 缓存只多了 `session` 一项配置，不改变来源校验与 baseURL；`.env.example` 里 `BETTER_AUTH_URL` 的要求不变。唯一依赖是各函数实例用同一个 `BETTER_AUTH_SECRET`——`session_token` 的签名本来就要求这样，`session_data` 用同一把密钥，不一致时只会让缓存验签失败、回落查库，不会出错。Secure：better-auth 1.7.10 的 `dist/cookies/index.mjs` 里 `session_token` 与 `session_data` 由同一个 `createCookie` 生成，同样跟随 `useSecureCookies`，所以在 Vercel 或 https 下两者都带 `__Secure-` 前缀和 Secure 属性；**这一点没有在 https 下实测**（本机是 http）。

### 发现 1–3 的处理（2026-10-17，分支 `claude/brave-leavitt-6caf3e`，基于 main `ac2eb6e`）

只改 `app/lib/tryon/nano.ts`、`app/lib/tryon/service.ts`，新增 `app/lib/tryon/delivery.test.ts`，以及本记录。没有用 fal key 调用，没有部署，没有连 Supabase；测试用临时目录里的 PGlite 与本地存储，fetch 全部替换。

**发现 2（轮询响应超过 Vercel 4.5MB）：选 (a)，再加一道兜底。**

- (a) `nano.ts` 提交体加 `output_format: "jpeg"`。fal OpenAPI（`https://fal.ai/api/openapi/queue/openapi.json?endpoint_id=fal-ai/nano-banana-pro/edit`，2026-10-17 核对）里该字段是 `jpeg | png | webp`，默认 `png`；FASHN 一直在用 jpeg（`fashn.ts`）。选它而不选 (b)（先写桶再返回地址）的理由：① 叠穿时下一步的底图本来就会被 `toJpegDataUri` 压成长边 1536、q92 的 JPEG，PNG 的无损对叠穿没有用，只影响最后展示的那一张；② 体积降一个数量级，手机下载和桶里存的都少；(b) 只是把 7MB 的 PNG 换成 302 后下载，字节没少，还要等写桶完成才能出细化图（本机写 7MB 要 20.6 s，那是上行很慢的热点网络，Vercel 上未测）。
- 兜底（`service.ts` 的 `deliver`）：随响应内联的 data URI 超过 3,500,000 字符（`inlineLimit`，4.5MB 上限留 1MB 余量）时，先写桶，响应里只给 `/api/avatar/files/<key>`（D64 已让该路由对 Supabase 驱动 302 到 120 s 签名链接）。覆盖快出图、细化、整套最后一步三处。写桶失败时既不返回 data URI，也不把这次试穿记为失败，只回报“处理中”，下次轮询重新取结果、重新写。这样无论 fal 实际给多大的图，响应都不会超限；要保留 PNG 时把 `NANO_OUTPUT_FORMAT` 改回 `"png"` 即可，超限的结果会自动走先写桶。
- 离线估算（**不是 fal 的编码结果**）：本机一张更早开发运行留下的 nano 细化结果（PNG，1792×2400，4,797,402 B，data URI 约 6.4M 字符）。只在内存里用 sharp 重编码，没有渲染、复制或提交：JPEG q75 134,941 B、q85 204,763 B、q90 309,734 B、q95 582,896 B，为 PNG 的 2.8%–12.2%，对应 data URI 约 0.18–0.78M 字符；相对原图 PSNR 43.9–46.6 dB。按这个比例，实测里 6.7–7.1MB 的 PNG 转成 JPEG 也远低于 3.5M 字符的内联上限。
- **未验证（合并 PR 时的状态；fal 的 JPEG 体积与画质已在 2026-10-22 补做真实确认，见下一条）**：fal 的 JPEG 实际体积与压缩质量（没有真实调用，fal 的 JPEG 编码参数未公开）；肉眼画质对比（没有渲染样张，PSNR 只是旁证）；Vercel 上 4.5MB 上限与 `after()` 行为；Supabase 上兜底路径（先写桶 + 302 取图）没有在真实 Supabase 上跑，单测用的是本地驱动。**决定**：2026-10-17，发起用户在 Claude Code 会话中回复“接受 JPEG，不做真实调用，按离线估算合并”。据此默认保留 JPEG，不做真实 fal 调用；fal 实际 JPEG 体积与画质仍是离线估算，上线后看到的第一批真实结果再复核（要改回 PNG 只改 `NANO_OUTPUT_FORMAT`）。
- **真实确认（2026-10-22 补做，1 次 nano-banana-pro 2K，约 0.15 美元）**：发起用户随后又在另一会话批准花不超过 0.30 美元做真实确认。10-17 那次提交因本机网络不稳（到 fal 的 TLS 握手 3–11 s，超过 30 s 提交超时）失败，请求没被 fal 接受，按“失败就停”没有重试；10-22 网络恢复后，用合并后的真实代码路径（`nanoBody` → `submitNano` → `fashnStatus` → `fashnResult`，`NANO_OUTPUT_FORMAT=jpeg`）提交 1 次。素材只用 AI 虚构模特 `O01.webp`（派生成 1044×1296 JPEG，293KB）和目录单品 `I006`。结果：fal 确实返回 JPEG（文件头 `ffd8ffe0`，data URI 头 `data:image/jpeg;base64`），**1,421,268 B（1.42MB），1792×2400，data URI 1,895,047 字符**，低于 3,500,000 字符的内联上限，不会触发先写桶兜底，响应约 1.9MB，在 4.5MB 之内；比之前的 PNG（6.7–7.1MB，data URI 8.9–9.5MB）小约 4.7–5 倍。它比离线估算（0.13–0.58MB，最高质量 q95）还大，说明 fal 的 JPEG 质量比 q95 更高或编码器不同，离线估算在体积上偏乐观，但余量仍足。耗时（家用网络）：提交 2.0 s，从提交到完成 29.2 s，取结果 2.3 s。画质：肉眼看 1792×2400 原图，人脸、羊毛面料纹理、衬衫纽扣、玻璃反光都清晰，没有可见的块状或色带；只有 1 个样本，不能代表所有单品。样图没有提交到仓库，测完已删除。仍未验证：Vercel 上 4.5MB 上限与 `after()` 行为、Supabase 上兜底路径（先写桶 + 302 取图）。

**发现 3（写桶完成前重复取结果、重复写桶）：加了幂等保护。**

- `service.ts` 里 `storing`：进程内按“记录 id + 阶段（fast / hq / chain）”打标记，在取回结果、决定写桶的那一刻就打上，写桶任务结束（`finally`）才清掉。有标记时，`advanceStep` / `advanceChain` 不再查 fal、不再取结果，只回报“还在处理”（细化阶段回报仍是快出图那张加“正在细化”）。标记 90 s 后失效，避免 `after()` 任务被丢弃时永远卡住。
- 写之前再读一次记录（`storeStep`、`storeChain`）：这个阶段已经有人写过就不再写；记录已被删除就不写，免得留下无主文件。这一道能挡住“另一个实例先写完、本实例的任务后到”。
- 局限：标记在进程内，Vercel 上多个实例之间不互斥，且没有人再轮询的记录，标记要到 90 s 失效后下次访问该记录时才清理（量极小）；刷新页面落到另一个实例时，仍可能重复取一次、重复写一次同一个 key（`x-upsert` 覆盖，只多花时间和流量）。跨实例的互斥需要数据库层面的占位，没有做。另一个可见的变化：写桶期间再次轮询，快出图阶段会看到几秒“生成中”（原先会再收到一份完整的 data URI），细化阶段看到快出图那张加“正在细化”。
