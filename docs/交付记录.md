发现（本轮只记录，没有改代码）：

1. **签名 URL 只省掉了底图那一份上传。**单品图 `garmentImage()` 对目录里的本站路径仍读成 data URI（53–102KB）；细化一段先用签名 URL 把底图下载回来（0.44–0.47 s），再缩成长边 1536 的 JPEG data URI 一起提交（请求体 477–536KB）。若正式环境单品图改传站点 https 地址，提交还能再省。
2. **细化结果是 6.7–7.1MB 的 PNG，随轮询响应返回时是 8.9–9.5MB 的 data URI。**Vercel 函数的请求/响应体上限是 4.5MB（官方文档，非流式），这个响应在 Vercel 上会因超限失败；本轮没有部署，**未在 Vercel 上验证**。D64 已把读已存文件的路由改成 302（见上表），但轮询响应里刚完成的结果仍是 data URI（合并后的 `service.ts` 仍返回 `got.dataUrl`），`nano.ts` 也仍没有设 `output_format`。fal 文档里 nano-banana-pro 的 `output_format` 支持 jpeg、webp（默认 png），改成 jpeg，或先写桶再只返回 files 地址，是两条路，需要决定。

### 发现 1–3 的处理（2026-10-17，分支 `claude/brave-leavitt-6caf3e`，基于 main `ac2eb6e`）

只改 `app/lib/tryon/nano.ts`、`app/lib/tryon/service.ts`，新增 `app/lib/tryon/delivery.test.ts`，以及本记录。没有用 fal key 调用，没有部署，没有连 Supabase；测试用临时目录里的 PGlite 与本地存储，fetch 全部替换。

**发现 2（轮询响应超过 Vercel 4.5MB）：选 (a)，再加一道兜底。**

- (a) `nano.ts` 提交体加 `output_format: "jpeg"`。fal OpenAPI（`https://fal.ai/api/openapi/queue/openapi.json?endpoint_id=fal-ai/nano-banana-pro/edit`，2026-10-17 核对）里该字段是 `jpeg | png | webp`，默认 `png`；FASHN 一直在用 jpeg（`fashn.ts`）。选它而不选 (b)（先写桶再返回地址）的理由：① 叠穿时下一步的底图本来就会被 `toJpegDataUri` 压成长边 1536、q92 的 JPEG，PNG 的无损对叠穿没有用，只影响最后展示的那一张；② 体积降一个数量级，手机下载和桶里存的都少；(b) 只是把 7MB 的 PNG 换成 302 后下载，字节没少，还要等写桶完成才能出细化图（本机写 7MB 要 20.6 s，那是上行很慢的热点网络，Vercel 上未测）。
- 兜底（`service.ts` 的 `deliver`）：随响应内联的 data URI 超过 3,500,000 字符（`inlineLimit`，4.5MB 上限留 1MB 余量）时，先写桶，响应里只给 `/api/avatar/files/<key>`（D64 已让该路由对 Supabase 驱动 302 到 120 s 签名链接）。覆盖快出图、细化、整套最后一步三处。写桶失败时既不返回 data URI，也不把这次试穿记为失败，只回报“处理中”，下次轮询重新取结果、重新写。这样无论 fal 实际给多大的图，响应都不会超限；要保留 PNG 时把 `NANO_OUTPUT_FORMAT` 改回 `"png"` 即可，超限的结果会自动走先写桶。
- 离线估算（**不是 fal 的编码结果**）：本机一张更早开发运行留下的 nano 细化结果（PNG，1792×2400，4,797,402 B，data URI 约 6.4M 字符）。只在内存里用 sharp 重编码，没有渲染、复制或提交：JPEG q75 134,941 B、q85 204,763 B、q90 309,734 B、q95 582,896 B，为 PNG 的 2.8%–12.2%，对应 data URI 约 0.18–0.78M 字符；相对原图 PSNR 43.9–46.6 dB。按这个比例，实测里 6.7–7.1MB 的 PNG 转成 JPEG 也远低于 3.5M 字符的内联上限。
- **未验证**：fal 的 JPEG 实际体积与压缩质量（没有真实调用，fal 的 JPEG 编码参数未公开）；肉眼画质对比（没有渲染样张，PSNR 只是旁证）；Vercel 上 4.5MB 上限与 `after()` 行为；Supabase 上兜底路径（先写桶 + 302 取图）没有在真实 Supabase 上跑，单测用的是本地驱动。JPEG 对画质的取舍由发起用户决定；如需用真实 key 确认，1–2 次 nano-banana-pro 2K 调用按官网单价约 0.15 美元一张，需用户同意预算后再做。

**发现 3（写桶完成前重复取结果、重复写桶）：加了幂等保护。**

- `service.ts` 里 `storing`：进程内按“记录 id + 阶段（fast / hq / chain）”打标记，在取回结果、决定写桶的那一刻就打上，写桶任务结束（`finally`）才清掉。有标记时，`advanceStep` / `advanceChain` 不再查 fal、不再取结果，只回报“还在处理”（细化阶段回报仍是快出图那张加“正在细化”）。标记 90 s 后失效，避免 `after()` 任务被丢弃时永远卡住。
- 写之前再读一次记录（`storeStep`、`storeChain`）：这个阶段已经有人写过就不再写；记录已被删除就不写，免得留下无主文件。这一道能挡住“另一个实例先写完、本实例的任务后到”。
- 局限：标记在进程内，Vercel 上多个实例之间不互斥，且没有人再轮询的记录，标记要到 90 s 失效后下次访问该记录时才清理（量极小）；刷新页面落到另一个实例时，仍可能重复取一次、重复写一次同一个 key（`x-upsert` 覆盖，只多花时间和流量）。跨实例的互斥需要数据库层面的占位，没有做。另一个可见的变化：写桶期间再次轮询，快出图阶段会看到几秒“生成中”（原先会再收到一份完整的 data URI），细化阶段看到快出图那张加“正在细化”。

**发现 1（单品图仍是 data URI）：只记录，没有改。** 把站点 https 地址交给 fal 需要 fal 能从公网取到这张图；受保护演示（Deployment Protection）下 `/catalog/items/*.webp` 预计会被挡在登录或密码页后面（没有部署，**未验证**），要放行得把绕过令牌放进地址交给第三方，不合适。收益也小：单品图只有 53–102KB，相比底图那一份已经由签名 URL 省掉了。部署之后若要做，先单独验证 fal 取不取得到，再决定用公开存储路径还是别的办法。
