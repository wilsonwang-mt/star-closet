# 交付记录

## 比赛版应用 · better-auth 会话 cookie 缓存：登录校验提速 · 2026-10-17（UTC+8）

依据：协调会话转达 D62 试穿在 Supabase 上的实测——慢链路上每个已登录请求要额外花约 0.64 s 做 better-auth 的 session 校验；任务是评估并开启 `session.cookieCache`，给出前后数字并写清安全取舍。分支 `claude/angry-khayyam-881925`（基于 origin/main `ad7a4a5`）。这是实现层调整，不改产品行为与授权边界，不新增决策编号（D64 已被部署授权占用，D65 为试穿提速）。

### 改动与 maxAge 的取舍

- `app/lib/auth.ts`：`betterAuth({ … })` 增加 `session: { cookieCache: { enabled: true, maxAge: 300 } }`。`app/README.md` 账号一条补了一句说明。
- **建议并采用 `maxAge: 300`（5 分钟，也是 better-auth 默认值）**：试穿的轮询每 1–2 s 一次，一轮试穿持续数十秒，5 分钟内的请求全部命中缓存，之后每 5 分钟只回库校验一次（约多花 0.6 s），体感无差；再拉长只是把撤销延迟变得更大、收益增加很小。本站没有改密、注销账号、“退出所有设备”、封禁这些会撤销会话的入口，撤销只来自“退出登录”，所以不需要更短的窗口。不启用 `refreshCache`（better-auth 在配置了数据库时会自己关掉它）。
- 机制（据 better-auth 1.7.10 源码 `api/routes/session.mjs`、`cookies/index.mjs`）：注册、登录和每次查库的 getSession 响应都会下发 `better-auth.session_data`（HttpOnly、SameSite=Lax、Max-Age=300；默认 `compact` 策略，用 `BETTER_AUTH_SECRET` 做 HMAC-SHA256 签名）。之后的请求带着它：验签、核对其中的会话 token 与 `session_token` cookie 一致、未过期，就直接返回，不查库；缺失、签名不对或过期才回落查库，Route Handler 里经 `nextCookies()` 重新下发，Server Component 里不能写 cookie，源码对这个异常是吞掉的（见下方实测）。

### 安全取舍（要知道的代价）

1. **撤销延迟最多 5 分钟**：会话在服务端被撤销或删除后，仍持有 `session_data`（连同 `session_token`）的客户端，在缓存有效期内仍被当作已登录。实测：删掉 session 行后，带完整旧 cookie 的请求仍通过（改前立即 401）；只带 `session_token` 的请求立即 401；`get-session?disableCookieCache=true` 查库为准，返回 null。
2. **同浏览器退出登录立即失效**（`sign-out` 同时清 `session_token` 与 `session_data`）。但退出前被复制走的整套旧 cookie，在 5 分钟内重放仍有效（实测改后仍通过，改前 401）。拿到整套 cookie 的人在用户退出之前本来就能以本人身份访问，新增的只是“退出或服务端撤销之后”最多 5 分钟的延迟。
3. **D47 不变**：私有照片与形象文件仍由服务端校验登录会话后按本人前缀读取，其他用户、主理人、品牌与运营没有访问入口；变的只是会话撤销最长晚 5 分钟生效。`session_data` 是签名、不是加密：载荷含 session（id、token、userId、expiresAt、ipAddress、userAgent）与 user（id、name、email、emailVerified、image）字段，约 0.9 KB，HttpOnly，页面脚本读不到；`user` 表没有额外字段，不含身体数据、照片或档案。需要加密时改 `strategy: "jwe"`。
4. **以后若增加改密、封禁、退出所有设备**：缩短 `maxAge`，对敏感操作传 `disableCookieCache`，或设 `cookieCache.version` 一次性作废全部已下发的缓存。现在没有需要这些的路由，没有预先加。

### D64 部署核对

`lib/auth.ts` 没有设 `trustedOrigins` 或 `baseURL`，cookie 缓存不改变来源校验与 baseURL；`.env.example` 里 `BETTER_AUTH_URL` 的要求不变。唯一依赖是各函数实例用同一个 `BETTER_AUTH_SECRET`——`session_token` 的签名本来就要求这样，`session_data` 用同一把密钥，不一致时只会让缓存验签失败、回落查库，不会出错。Vercel 的 https 下 cookie 名会自动带 `__Secure-` 前缀，两个 cookie 同样处理，**这一点没有在 https 下实测**（本机是 http）。
