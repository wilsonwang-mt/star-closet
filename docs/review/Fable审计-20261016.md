## 1. 执行摘要

**一句话判断**：这是一件"7 分的皮、5 分的骨"的作品——视觉语言、动效词汇和微文案已经明显高于比赛作品的水准，深色手机视口下的首页轮播与"走进衣橱"是真实成立的签名时刻；但冷启动、性能预算、流程收口和跨页一致性还停留在"各自为政"的阶段，离 apple.com 新品页的差距主要不在画面，而在**每一次等待和每一次衔接**。

**三个最大的问题**：
1. **链条会断**：目录 100% 依赖 Supabase、AI 调用没有超时（SDK 默认 10 分钟）、匿名改编后点"加入试衣间"跳登录并丢掉结果——评委最可能走的路径末端没有收口（FA-01、02、04）。
2. **首次进入没有被设计**：首页 300ms 就是完成态、没有任何进场；弱网下页面"看起来已就绪"但 16 秒不可拖拽、无任何反馈；1.95MB 字体 + 3MB 视频 + 串行查库决定了这个体验（FA-09～12，维度 E）。
3. **衔接处有空档**："走进衣橱"点击后 0.18–0.5s 静止、弹簧到位后又有 0.45s 静止尾巴、文字 0.975s 才起身；衣橱→搭配没有共享元素过渡；改编等待→结果是跳切（FA-07、19、20）。

**三个最大的机会**：首页加一个由真实事件驱动的"开场"（§4，S–M）；用 settle 时长重排"走进衣橱"的三段节奏（S，立刻可感）；把价格/标题/徽章/外链这些"评委一眼就看到的不一致"一次清掉（合计 S）。

**截止前怎么取舍**：只做 P0 三件 + 约 10 件 S 级 P1（§5 第一段，合计约 6–7 小时），其余一律截止后。演示用桌面 Chrome 投屏 + 430px 窗口展示手机视口，预登录、预生成 3D、不现场说话、不点淘宝外链（§6）。

## 3. 发现清单

格式：严重度 · 维度 · 现象 → 证据 → 根因 → 建议（文件 / 改法）→ 工作量（S<1h / M 半天 / L 一天+）/ 时机。

### P0 · 阻断演示

**FA-01 · L/I · 演示没有离线兜底：目录 100% 走 Supabase，AGENTS.md 声称的 JSON 兜底不存在**
- 证据（事实）：`app/lib/catalog.ts` 全部查询直连 `lib/db`，`grep catalog.json app/lib/*.ts` 为空；`app/lib/db/index.ts:9-20` 只在没有 `DATABASE_URL` 时用 PGlite；`AGENTS.md`「静态目录 JSON 保留为兜底，Supabase 不可用时演示仍能运行」在代码里没有对应实现。
- 根因：目录层只有 DB 一条读路径。
- 建议：截止前（S）准备第二套环境 `app/.env.demo-local`（去掉 `DATABASE_URL` / `DATABASE_MIGRATE_URL`，其余同 `.env.local`），提前 `npm run db:setup` 建本地 PGlite 库，注册演示账号、存 1–2 套搭配、预生成一个 3D 形象；写 `demo.sh` 一键切换 env 并 `next start`。截止后（M）在 `lib/catalog.ts` 每个导出函数外包一层 try/catch，失败时回落读取 `data/catalog.json`（可复用 `scripts/setup-db.ts` 的解析逻辑）。
- S / 截止前（备份方案）。

**FA-02 · I/L · AI 改编没有任何超时，用户也没有取消出口**
- 证据（事实）：`app/lib/adapt/ai.ts:58` `new Anthropic()` 未设 `timeout`/`maxRetries`（SDK 默认 600000ms、重试 2 次），`:81` 外层还有 2 次 attempt；`app/components/Adapter.tsx:78` fetch 无 `AbortController`；`AdaptWaiting.tsx:9,22` 五句文案 10 秒后用尽；实测正常一次 14.8s（`adapt-waiting-mobile-5s.png`）。
- 根因：等待路径只设计了"最短 900ms"，没有"最长"。
- 建议：`ai.ts:58` 改 `new Anthropic({ timeout: 20_000, maxRetries: 0 })`（超时会自然落到 `route.ts:28-34` 的规则模式回退）；`app/app/api/adapt/route.ts` 加 `export const maxDuration = 60`；`Adapter.tsx adapt()` 用 `AbortController` 45s 超时 + 等待卡右上角「取消」按钮，超时文案「这次改编超时了，再试一次」；`AdaptWaiting` STEPS 追加「再核对一遍预算与类别…」「快好了…」，`s>18` 时右上角改「比平时慢一点 · 19s」。演示保险：`route.ts` 加落盘缓存（`app/.data/adapt-cache.json`，key = outfitId|request），彩排时把演示句子各跑一遍。
- S / 截止前。

**FA-03 · L · 演示环境与数据状态没有固化（Supabase 是否 v0.2、.next 是否与代码一致、减弱动态 / 低电量、字体构建依赖、局域网登录）**
- 证据（事实 + 推断）：交付记录 :126 写"用户 Supabase 尚未执行迁移与 v0.2 写入"，而本次实测首页已是 `01 / 10`（`home-mobile-dark.png`）且测试账号成功写入——运行实例连的是 `.env.local` 的 `DATABASE_URL`，推断库已是 v0.2，但没有直接查库核对，演示前必须核对；`.next` 构建依赖 Google Fonts 网络（交付记录 :27 曾失败一次）；减弱动态下整站不挂视频、不放大（`home-mobile-dark-rm.png`）；`app/lib/auth.ts:7-22` 无 `trustedOrigins` 且 `BETTER_AUTH_URL=http://localhost:3000` → 手机走局域网 IP 时注册/登录会被 better-auth 来源校验拒绝（推断，源码 `origin-check.mjs` 已核对）。

- S / 截止前。

### P1 · 明显拉低品质

**FA-04 · C/I · 匿名用户改编后点「加入试衣间」被送去登录，回来改编结果已丢失**
- 证据（事实）：`save-anon-redirect-mobile.png`（整屏只剩登录表单，无任何来意说明）；`Adapter.tsx:143-146` 401 分支直接 `router.push('/login?next=…')`，之前没有任何暂存；`result/items/request/before` 全是组件内 state；`save()` 无 try/catch、可重复提交（`:129-152`、`:308-314`）。
- 根因：保存动作前置了登录，但改编状态只活在内存里。这是整条路径里最有价值的瞬间被打断并清零。
- 建议：`save()` 401 分支改为先 `sessionStorage.setItem('sc-adapt:'+outfit.id, JSON.stringify({request,result,items,before,pendingSave:mode,at:Date.now()}))` 再跳 `/login?next=/outfit/<id>&reason=save`；`Adapter` 挂载时读同一 key（30 分钟内有效）恢复四个 state、滚到结果卡并自动重试保存；`login/page.tsx` 读 `reason=save` 时 kicker 改「Save to fitting room」、副题「登录后会回到你刚改编的那一套」。同时加 `saving` 态（按钮「加入中…」、禁止重复提交）与 try/catch 中文兜底。
- M / 截止前（演示另用预登录账号规避）。

**FA-05 · C · 保存成功后是死胡同：只有徽章，没有去试衣间的入口**
- 证据（事实）：`outfit-saved-mobile.png`（"原样加入试衣间"右侧只有徽章）；`Adapter.tsx:179` 徽章无链接，`:308-314` 主按钮变成禁用的「已加入试衣间」；去试衣间唯一路径是汉堡菜单。
- 建议：徽章改为 `<Link href="/fitting-room" className="sc-badge">已加入 · 去试衣间 →</Link>`；主按钮在 `saved === result.mode` 时渲染为 `<Link href="/fitting-room?new=<lookId>" className="sc-cta">去试衣间看看</Link>`（`save()` 成功后保存返回的 id），右侧保留「重新改编」；试衣间读 `?new=` 给对应卡一次金线扫过（`globals.css` 已有 `row-sweep`）。
- S / 截止前。

**FA-06 · C · 首屏不说「这是什么、能做什么」，核心能力「一句话改编」藏在第三层**

**FA-07 · D · 「走进衣橱」的三段节奏有两处空档：点击后 0.18–0.5s 静止；弹簧 0.54s 已视觉到位但 VT 跑满 0.925s，交叉淡化排在静止尾巴里；文字 0.975s 才浮起**
- 证据（事实）：有头 Chrome 录屏抽帧 `vt-filmstrip-enter-mobile.png`：0–400ms 画面与点击前几乎相同，500→1400ms 放大，1500→2000ms 文字浮起；`enter-gap.mjs` 6 次拆分：按下态 ~10ms → `startViewTransition` 130ms（`PRESS_MS=120`）→ 新页面就绪 171–192ms（4 次）或 480–500ms（2 次，预取未命中）；`lib/motion.ts` `springs.enter(90/16)` 数值积分：进入 1% 误差在 537ms，而 `restDelta 0.0005/restSpeed 0.002` 让 `springCss` 返回 925ms；`globals.css:505-506` old/new 的 `animation-delay: calc(var(--vt-dur) * .55)`（=509ms）；`ClosetExperience.tsx:83` `base = duration/1000 + 0.05 = 0.975s`。
- 根因：三个时长都派生自"程序静止"而不是"看起来停了"；预取与 VT 冻结之间没有即时反馈。
- 建议：(1) `motion.ts` 增加 `settle(spring, eps=0.01)` 并让 `springCss` 返回 `{easing, duration, settle}`，VT 时长用 `settle × 1.15`（≈620ms）、`restDelta/restSpeed` 交给 Motion 默认；(2) `globals.css` enter 方向的 old/new 交叉淡化改到 `animation-delay: calc(var(--vt-dur) * .12); animation-duration: calc(var(--vt-dur) * .3)`（放大最快的阶段吞掉裁切差）；(3) `ClosetExperience.tsx:83` `base = settle/1000 − 0.05`（文字在画面停稳前 50ms 起身）；(4) `PRESS_MS` 120→60，并在 `enter()` 里给 `section.root` 加 `data-leaving` 让标题/信息 150ms 内淡到 .35（冻结前就有"出发"反馈，也符合规范 §7.1「文字先淡出」）；(5) `next.config.ts` `experimental.staleTimes: { dynamic: 60 }`，让已预取的衣橱页在 60 秒内复用，不再出现 0.5s 的最坏情况。
- S / 截止前。

**FA-08 · D · 吸附后约 480ms 内点中央卡会被当作"抓住"：看起来停了，点了没反应，再点才进**

**FA-09 · F/E · 中文字体走 Google 切片声明：首页触发 32 个 woff2 共 1.95MB，弱网 12.7s 才全到、分片 FOUT；JS 排在字体和图片之后，Fast 3G 下轮播 16 秒不可拖且无任何反馈**

- 根因：next/font/google 对 CJK 只能按 Google 的 101 片 unicode-range 子集声明；每多一个字重就多一整套；页面没有"可交互"信号。
- 建议：截止前（S）：`layout.tsx` 两款 CJK 字体各只保留一个字重（400；300 用 `font-weight: 300` 合成或改用 400 + 颜色降级），下载量减半、CSS 减半。截止后（M）：用 `pyftsubset` 按 `data/catalog.json` 全部字符串 + `app/**/*.tsx` 文案生成 4 个自托管子集（约 1500 字，合计 ≈1.2–1.6MB → 4 个请求、一次换字），`next/font/local` 引入并 `preload: true`；与 §4 的进场编排配合，让"字体就绪"成为一个可见事件。

**FA-10 · F/D · 手机上每切一间衣橱立刻挂载一个 preload=auto 的 3MB 视频（4.3Mbps，约为所需 4 倍）；桌面与宽屏完全没有视频**
- 证据（事实）：实测冷启动切两间后视频累计 6.4MB；`ClosetCarousel.tsx:518` `playVideo = i === active && …` 直接跟 active（环境光却有 220ms 去抖 `:384-386`）；`SceneVideo.tsx:54` `preload="auto"`；`public/catalog/curators/C0X-closet.mp4` 540×960 / 6s / 3.1–3.3MB；桌面 `wide===false` 才挂视频（`:518`、`ClosetExperience.tsx:106`）。
- 建议：(1) `playVideo={c.id === ambientId && …}` 复用 220ms 去抖，拖拽期间只显示海报；`SceneVideo` 的 `preload` 改 `"metadata"`；(2) 截止后用 ffmpeg 重编 10+4 段：`-vf scale=720:1280 -c:v libx264 -crf 27 -maxrate 2.6M -movflags +faststart -an`（约 1.7–2.0MB，且不再在 3x 屏上放大 2.1 倍），再出 HEVC 版给 Safari；(3) 之后给每间衣橱补横版视频（Weave 生成），桌面投屏才有"电影感的核心证据"（现在桌面首页/衣橱页是静态图缓推，`home-desktop-dark.png`）。

## 4. Loading / 首次进入方案

### 4.1 现状与约束

- **现状**：没有站点级进入体验。首页 300ms 即完成态（`home-mobile-dark-first.png` 与稳定态一样）；路由骨架（`Skeletons.tsx`）与真页同位、CLS=0，但预取命中时只闪几十毫秒。冷启动的真实时间线（手机，本地网络 / Fast 3G / Slow 3G）：HTML 0.17s / 0.14s / 0.13s → 首张海报 0.19s / 1.5s / 3.5s → FCP 0.29s / 2.3s / 8.2s → 字体全到 0.25s / 12.7s / 52s → 水合（可拖）0.41s / ≈16s / ≈65s → 视频可播 ~1s / 未缓冲 / 未缓冲。**最长的一段是"看起来已就绪 → 真的能用"**：弱网下这段长达十几秒，页面没有任何信号。
- **可用的真实事件**：① 海报 `load`/`decode()` 完成（本地 191ms / Fast 3G 2.07s；可由 `<body>` 首子节点的内联脚本在捕获阶段监听 `[data-vt-hero] img` 的 `load`，不依赖水合）；② 字体就绪——**注意 `document.fonts.ready` 在 174ms 就 resolve（字体尚未请求），不能当门**，要用 `document.fonts.load('400 28px "Noto Serif SC"', 标题文案)` 与 `fonts.load('400 15px "Bodoni Moda"', 'STAR CLOSET')` 并设 1.5s 上限；③ 水合完成（`ClosetCarousel` 的 `useLayoutEffect` 已有 `signalHeroReady()`，同一处写 `html[data-hydrated]`）；④ 中央视频 `playing`（`SceneVideo` 已有 `onPlaying`）；⑤ 首个 RSC 完成（仅对衣橱/搭配页有意义）。事件在弱网下相差一个数量级（海报 2s、字体 13s、JS 16s），所以不能"等齐"：到一个揭示一层。
- **硬约束**（任务书）：不做假进度条；有内容就不被挡住；只在冷启动出现、站内路由沿用共享元素过渡；与品牌气质一致；减弱动态下全部退化为淡入；可跳过。
- **前置依赖**：FA-09（字体）与 FA-12（LCP 预加载、staleTimes）决定了事件到来的时间；进场编排只能**如实呈现**等待，不能缩短它。

### 4.2 三个概念

**概念一 · 「一束光里的衣橱」（电影开场，推荐）**
- 一句话：冷启动时，画面从一束光开始，衣橱从虚焦推到清晰，然后浅弧"扇开"——每一幕都由一个真实事件触发，资源快时整段压缩到 0.4s 几乎不可见，资源慢时它就是等待本身。
- 分镜（手机）：
  - 0ms（HTML + 关键 CSS）：深石墨底；刊头 `STAR CLOSET` 与刊号 `N°01 — Night Edit`（Bodoni，latin 子集已 preload，31KB）以 0.6s 浮起；一道射灯光束（`.sc-beam`，tokens 已有）呼吸。没有任何 spinner。
  - 事件① 海报解码：中央卡从 `blur(6px) brightness(.5) scale(1.08)` 推到清晰（规范 §7 的虚焦进场，但由解码驱动、时长 0.6s）。此时卡片是静态的单张（无侧卡）。
  - 事件② 字体就绪（或 1.2s 上限）：「想走进谁的衣橱？」、主理人名、tagline 以 `sc-rise` 依次浮起（CJK 文字在此之前 `opacity: 0`，避免换字闪；超时则用回退字体直接浮起）。
  - 事件③ 水合完成：两侧卡片从中央卡背后"扇开"到浅弧位置（`pos` 从 0 弹到各自位置，用 `springs.step`），切换按钮与计数器浮起——**扇开就是"现在可以拖了"的信号**。
  - 事件④ 视频开始播放：海报 → 视频交叉淡化（现有逻辑）。
  - 热缓存：①②③ 在 300ms 内相继到达，CSS 过渡自然叠成一个 0.4s 的整体淡入，不增加任何等待。
- 状态机：`html[data-boot]` ∈ `cold → poster → fonts → ready`（单调递进，允许跳级）；`cold` 由 `<head>` 内联脚本在"首次访问（`sessionStorage.sc-seen` 不存在）且 `navigation.type === 'navigate'`"时设置，否则不设（站内导航、刷新、bfcache 都不走这套）；`poster` 由 `ClosetCarousel` 服务端渲染出的一段 `<script>`（或 CSS 内联脚本）对中央海报 `new Image().decode()` 后设置；`fonts` 由 `document.fonts.ready.then()` 与 1.2s `setTimeout` 竞速；`ready` 在 `useLayoutEffect` 里设置并写 `sc-seen`。任何一步失败（解码报错、字体超时）都只是跳到下一态。
- 技术路径：全部用 CSS `transition`/`animation` 对 `transform/opacity/filter`，按 `html[data-boot="…"]` 选择器控制 `.head`、`.stage`、`.info`、`.controls` 的初始状态；侧卡"扇开"是把 `pos` 的初始值设为"全部堆在中央"并在 `ready` 时 `animate(pos, startIndex, springs.step)`（`ClosetCarousel.tsx` 的 `useLayoutEffect` 里已经有恢复 `pos` 的逻辑，加一个 `boot === 'cold'` 分支即可）；与 FA-39 合并：未测量/未水合前本就该只显示中央卡。与 View Transition 的衔接：`data-boot` 只在首页冷启动存在，`navigateWithHero` 不受影响；衣橱页直接冷打开时沿用规范 §7 现有的 3s 虚焦（建议同样改由海报 `decode()` 驱动并缩到 1.2s）。
- 手机预算：新增 0 个资源；`<head>` 内联脚本 ≈200B；CSS ≈40 行；JS 改动集中在 `ClosetCarousel.tsx` 的两个 effect。对 LCP 无负面影响（海报仍是最早出现的大元素；注意 `blur` 进场不应把 LCP 元素长期置于 `opacity:0`，改用 `filter` 不改 `opacity`）。
- 减弱动态：`data-boot` 各态只切 `opacity`（0.2s），不做模糊、缩放、扇开；侧卡直接出现。
- 可跳过：任何 pointerdown / keydown 立即把 `data-boot` 置为 `ready`（CSS 过渡会从当前值继续）；整段最长不超过 4s（字体上限 1.2s + 水合不等待，即使水合要 16s，扇开只是晚到——用户看到的是"可以看、还不能拖"的真实状态，中央卡上方可在 `ready` 之前显示一条 LinkPending 同款的细线作为"还在准备"的诚实提示）。
- 工作量：最小版（两个标志 + 文字/卡片淡入 + 扇开）S–M（约 3 小时）；完整版（光束开场、衣橱页冷启动同一套、字体子集）M+。
- 风险：`<html suppressHydrationWarning>`（脚本改 html 属性，React 19 dev 会报属性差异；next-themes 同法）；`sessionStorage` 不可用时按 `cold` 处理一次即可；扇开动画与 `warmCloset` 的 400ms 预取定时器不冲突；推清期间点「走进衣橱」要在 `[data-pressed]` 时 `animation: none` 清掉虚焦，否则 VT 会截到模糊帧。
- 评审团"电影开场"角度的实现补充（建议直接采用）：(1) 不用线性状态机，用 `<html>` 上 4 个**互相独立**的标志位——`data-intro-type`（Bodoni `fonts.load` 兑现，上限 600ms；刊头/引题/标题可出现）、`data-intro-scene`（海报 `decode()` 兑现，上限 1.5s；推焦开始、底色罩 .55→0、信息/CTA/控件按固定偏移浮起）、`data-live`（`signalHeroReady()` 里 `dispatchEvent(new Event('sc:live'))`，就是现成的"水合完成"事件，无上限、不伪造）、`data-intro-skip`（任一输入 → 全部时长 ×0.3）——实测里事件先后随网络完全颠倒（本地 字体 182 < 海报 191 < FCP 288 < 水合 413；Fast 3G 是 Bodoni 923 → FCP 2272 → 字体 1–13s → 水合 16.2s），CSS 对每个标志独立响应，任何顺序都成立；(2) 水合前控件（筛选 chip、箭头、计数器、索引行）停在 `.55` 压暗而不是隐藏，本地网络下水合早于它们浮起所以看不出这一拍，Fast 3G 下它们保持 .55 约 13 秒——如实表达"轮播还不能拖"，正是实测点名的那 16 秒零反馈；(3) `globals.css` 给 `html` 补 `background: var(--sc-bg)`（现在只有 body 有，首帧与 iOS 回弹区会露白）；(4) 进入条件在 `<body>` 首子节点的内联脚本里判定：`pathname === '/'` 且 `navigation.type === 'navigate'`（reload / back_forward 不播）且 `sessionStorage.sc-intro` 未设，`?intro` 可强制重放用于演示；(5) 可选一拍（需你拍板）：推焦 +3s 仍未 `live` 时，计数器下方那条 72px 发丝线做不定式扫光（复用 `row-sweep`），这是"仍在准备"的不定式提示，不是进度条。

**概念二 · 「刊头页」（杂志开场，最克制）**
- 一句话：像翻开一本杂志的刊头页——`STAR CLOSET` 字距从 .2em 展开到 .42em、下方一条 1px 金线从中间向两侧划开、刊号 `N°01 — Night Edit` 浮起——总长 ≤ 700ms，只在冷启动出现一次，之后整页淡入。
- 分镜：0–300ms 刊头字距展开 + 金线划开；300–600ms 刊号浮起；事件①（海报解码）或 700ms 到达时整页从刊头页下方淡入（刊头页本身就是最终导航胶囊里的刊头字，用 View Transition 的 `view-transition-name: masthead` 让它"飞"进胶囊）。
- 状态机：只有 `cold → ready`；`ready` = 海报解码 ∧（字体就绪 ∨ 1.2s）；水合晚到不影响（页面可看）。
- 技术：纯 CSS + 一个内联脚本；`view-transition-name` 复用现有 VT 基建。
- 优点：几乎零风险、最贴"杂志感"、工作量 S。缺点：它不解决"看起来能用但不能用"的问题（水合不是它的事件），只是一次品牌亮相；资源快时它反而是唯一可见的 0.6s——这正是"增加感知等待"的边缘，需要把 700ms 压到 450ms 并在海报就绪时立刻结束。
- 评审团"杂志刊头"角度的实现补充（解决了上面的缺点）：刊头页**住在导航胶囊落下之前那 0.3–0.9 秒的空档里**——胶囊今天本来就有 .2s 延迟 + .9s 弹簧落下，刊头（左 `STAR CLOSET` 11 个字母从 `translateX(-i×.3em)` 展开、右 `N°01 — Night Edit` 斜体淡入、下方 1px 金线从左描出）占用的正是这段空档，页面文案从首帧照常浮起、不扣一帧；出口取先到者：① `SiteNav` 挂载 effect 派发 `sc-intro:ready`（等价于整棵树水合完成）、② 首帧起 900ms 上限、③ 用户输入；reveal 时刊头 .35s 溶出、胶囊恢复落下、品牌字在同一左缘接替；水合迟到（上限触发）时胶囊品牌字下留一条 1px 香槟金线以 2.4s 呼吸，直到 `sc-intro:ready` 才收回——它不表示百分比，只说明"脚本还在路上"。本地实测胶囊落稳只比今天晚约 130ms，可交互时刻完全不变。

**概念三 · 「资源编排」（工程优先，无品牌动作）**
- 一句话：不加任何仪式，只把现在"一次性出现"改成"按到达顺序揭示"：海报 → 文字 → 侧卡 → 视频，每层到了就淡入；并把 FA-09/10/12 的资源优先级修正作为方案的一部分。
- 它与概念一共享同一个状态机和 CSS，只是没有光束与虚焦推清，文字也不等字体（直接 FOUT）。
- 优点：最省、最诚实；缺点：没有记忆点，评委感受不到"进入仪式"。

**概念三的详细版（评审团"资源编排"角度产出，命名「对焦 · 开门」）**与概念一高度重合，补充了三个值得直接采用的实现细节：(1) SSR 就渲染"一张静止的中央卡 + 收拢在它背后的侧卡"（`place()` 的全部几何乘以 `open`，`open=0` 时侧卡 x/z/rotateY/blur 归零、opacity 0），水合时 `animate(open, 1, springs.rise)` 扇开——未水合前侧卡本就拖不动，藏起来是诚实的；(2) 海报事件用 `<body>` 首子节点约 330B 的内联脚本在捕获阶段监听 `load`/`error`，命中 `[data-vt-hero] img` 时写 `html[data-poster]`，海报先于 CSS 到达也能正确起手，`error` 时只保留"未亮灯的门"面板不做动画；(3) 视频在弧停稳（`animate().then`）之后才挂载，不与展开弹簧抢主线程。它还提出一个需要你拍板的取舍：**正文是否改用系统字体**（删掉 Noto Sans SC，`--sc-font-sans` 改 `-apple-system, "PingFang SC", "Noto Sans CJK SC", "Microsoft YaHei"`，只为杂志感的 Serif/Didone 付网络代价；参照 apple.com.cn 界面文字用系统字体），字体从 1.95MB/32 文件降到约 0.6MB/12 文件、字体声明 CSS 从 127KB 降到 32KB gz，Fast 3G 的 FCP 预计 2.3s → 1.4s；代价是 Windows 上正文变雅黑。

**推荐**：概念一，用概念三的状态机与上述三个实现细节做底、概念二的刊头字距作为第一幕的点缀（刊头 + 刊号在 0ms 就出现，是三个概念里唯一不依赖任何资源的"品牌一秒"）。实施顺序：先做 FA-12（LCP preload）与 FA-09 最小版（字重减半或正文系统字体，需拍板），再做 `data-poster / data-hydrated` 两态与扇开（S–M），光束、微尘与衣橱页同套（M）放截止后。评审团（设计总监 / 动效工程师）的打分见 §7.7。

### 7.7 Loading 评审团
三个角度的概念（电影开场「暗场一束光」、杂志刊头「Masthead Plate」、资源编排「对焦 · 开门」）均已产出并并入 §4；两位评委（设计总监 / 动效工程师）的打分因用户要求控制 token 成本而在完成前停止，§4 的推荐是主会话基于三个概念自行综合的结论：以"对焦 · 开门"的独立标志位状态机与 SSR 收拢侧卡为底，取"暗场一束光"的控件 .55 未就绪态与 `html` 底色修正，取"Masthead Plate"的刊头字距展开与水合迟到时的呼吸金线。三者一致的硬约束核对结论：无进度条、不遮已到内容、只在文档冷启动、减弱动态只淡入、任一输入即快进。
