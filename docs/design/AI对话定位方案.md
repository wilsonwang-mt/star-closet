# AI 对话定位衣橱与搭配 · 设计方案（D52 → D56）

> **2026-10-16 19:20 更新（D56，以本节为准）**：用户要求“这个 AI 对话的功能应该今天就开发完，最好是，AI chat 窗口一直悬浮在界面右下角。这样，我随时可以给输入，然后对话窗口中通过 Gen UI 的方式把结果产出出来，并且可以进行交互直接跳转到对应的衣橱页面，或者某个功能页面。”据此入口从“首页标题旁”改为**全站右下角悬浮对话**，并且今天实施，不再等确认。下文 §0–§7 的映射规则（§3）、两段式等待（§4）、不进 URL 的句子传递与 D48 文案约束继续有效；§2 入口与 §5.1 轮播转向被本节替代。
>
> **D56 实施范围**
> 1. **入口**：右下角圆形玻璃入口挂在根布局，与 `SiteNav` 同级，每页都在。手机点开是底部抽屉（模态，带遮罩），桌面是右下角浮窗（非模态，可以边聊边看页面）。遇到吸底操作条（`.cta-bar`）时，手机上入口停靠进操作条右侧，成为主按钮旁的圆形次按钮（视觉规范 §2 第 4 层），操作条右侧留位，不盖主按钮；带 `data-dock-avoid` 的元素则让入口抬到它上方。对话状态放在布局层，路由切换不丢；sessionStorage 持久，刷新后还在。
> 2. **Gen UI**：回复是“一句话 + 可交互卡片 + 追问 chip”。卡片有三种：衣橱卡（封面、头像、衣橱名、tagline → `/closet/[id]`）、搭配卡（封面、N°、总价 → `/outfit/[id]`）、功能卡（试衣间、3D 形象、2D 试穿、个人档案、登录、全部衣橱）。AI 通过 Claude tool use 调用 `show_closets` / `show_outfits` / `open_page` / `suggest_replies`，只返回 id；服务端按目录校验 id（不在目录、性别不符都丢弃），再把 id 解析成卡片数据，前端只按数据渲染。
> 3. **速度**：服务端先跑规则（§3 的解析与打分，`lib/locate/`），第一行 NDJSON 在目录读取后立刻返回卡片和一句话（目录在服务端内存缓存 5 分钟）；随后流式输出 Claude 的文字，结束时用 AI 的卡片替换规则卡片。没有 `ANTHROPIC_API_KEY`、超时（首字 10 秒、整轮 25 秒）或出错时停在规则结果，不加任何“规则模式”提示（D48）。
> 4. **模型**：`claude-opus-5-5`，`effort: low`，**fast mode**（`speed: "fast"`，beta `fast-mode-2026-02-01`；用户随后说“采用 Opus Fast Mode 吧”），流式输出，`maxRetries: 0`，目录放进可缓存的系统提示。fast mode 未开通或被限流（400/403/404/429）且还没流出文字时，自动用标准速度重试一次；标准速度下开启服务端 `fallbacks: "default"`。`CHAT_SPEED=standard` 可关掉 fast，`CHAT_MODEL` 可换模型，都不改代码。实测fast：4 句样例中 3 句首段文字 1.9–2.3 秒、整轮 2.6–3.2 秒（标准速度同 3 句 2.8–4.5 / 5.3–6.6 秒）；“暖一点的颜色”一句模型思考更久，fast 首字 9.5 秒、标准 10.7 秒。首个反馈仍靠规则保证。
> 5. **首页**：标题同一行加一枚引导胶囊“告诉我场合和预算”，点开就是同一个悬浮对话；不加筛选（D51）。
> 6. **视觉**：玻璃、香槟金、Bodoni 引题，深浅两种主题都成立；开合用 `lib/motion.ts` 的弹簧，减弱动态只淡入。键盘可达：Esc 关闭并把焦点还给入口，手机抽屉内 Tab 循环；`role="dialog"`，最新回复进 `aria-live` 区。

## 1. 范围

**要做的**：用户说一句话（场合、风格、预算、性别、想像谁），产品替他在 10 间衣橱、60 套搭配里定位到「哪一间、哪一套」，并接上已有的「走进衣橱 → 搭配 → 一句话改编」链路。

**不做的**：
- 不做通用聊天机器人，不闲聊，不回答目录以外的问题。
- 不代替用户加入试衣间或购买（FR03 授权边界）。
- 不在定位阶段改搭配。改搭配仍由搭配页的一句话改编负责，定位只负责把话带过去。
- 不存用户的话：不落库，服务端日志只记状态码和耗时，不记正文。

**和现有能力的关系**：一句话改编回答的是「这套怎么改成适合我」，对话定位回答的是「我该先看哪一间、哪一套」。两者同一个输入习惯，同一套解析，前后接力。

## 2. 入口位置

### 2.1 竖向预算

手机卡片高 `--card-h: clamp(300px, calc(100svh - 356px), …)`，356px 已经是导航、刊头、标题、信息区、切换行的总和，首屏按刚好放满设计。**新加一整行输入框，卡片就要矮 52px**；在 667 高的小屏上（667 − 356 − 52 = 259）会触到 300px 下限，把切换行挤出首屏。所以入口不能单独占一行。

## 3. 一句话怎么映射到 10 间衣橱、60 套搭配

### 3.1 目录事实（决定了映射方式）

| 字段 | 分布 | 推论 |
| --- | --- | --- |
| `style_tags` | 27 个值。每间衣橱 3 个，**同一间的 6 套完全相同** | 风格词只能区分衣橱，区分不了同一间里的搭配 |
| `occasion_tags` | 23 个值（周末 13、通勤 11、聚会 11、约会 8 … 年会 1） | 场合是定位到具体那一套的主信号 |
| `budget_tier` | 平价 4 套（¥894–1,125）、适中 28 套（¥1,235–1,984）、进阶 28 套（¥2,004–3,454） | 有具体数字时按单品价格合计判断；只说了「便宜点」「学生党」「质感好一点」这类模糊词时才用 tier |
| `gender` | 女装 42 套 / 7 间，男装 12 套 / 2 间（C08、C09），中性 6 套 / 1 间（C10） | 说了性别就硬过滤；没说时可能出现跨性别平手（§3.4） |
| `season` | 秋冬 54 套，四季 6 套，没有春夏 | 「夏天」「很热」在目录里没有对应搭配，要如实说明 |
| 主理人 | 10 位虚构主理人，没有真实明星 | 「像 Vera」可以直达；「像某位明星」规则层没有对应（§7 决策项 ③） |

### 3.2 解析：一句话 → 查询

```ts
// 设计草图，不是实现
type LocateQuery = {
  person: string | null;        // 主理人 curator_id：中英文名、衣橱名都算（林薇 / Vera / 静奢通勤 → C01）
  styles: string[];             // → style_tags；同义词：老钱/高级感→静奢，国风/马面裙→新中式，暖色/焦糖→美拉德 …
  occasions: string[];          // → occasion_tags；同义词：草坪婚礼→户外婚礼，爬山/徒步→户外+运动，过年/见亲戚→节日+聚会 …
  generic: boolean;             // 只说了 周末 / 日常 / 休闲 / 逛街 这类泛场合
  avoid: string[];              // 否定：「别太正式」→ 正式；「不要皮革」照旧交给改编
  gender: "女装" | "男装" | null; // 男生/男朋友/老公/给他 → 男装；女生/女朋友/裙 → 女装
  budget: number | null;        // 复用 parseConstraints 的预算正则（与改编同一份理解）
  tier: "平价" | "适中" | "进阶" | null; // 只在没有数字、出现模糊预算词时填
  season: "春夏" | "秋冬" | null;
  sizes: SizeWish;              // parseSizes，原样带给改编
  recognized: boolean;
};
```

三条解析规则，都来自原型跑出来的问题：

1. **最长匹配，命中后消费原词**。先匹配「户外婚礼」，再从文本里删掉它，免得「户外」再命中一次变成「户外 + 运动」。原型第一版就出现过这个问题。
2. **否定窗口**：`别太|别|不要太|不要|不想|不用|不穿` 后面 1–4 个字记入 `avoid`，并从正向匹配里去掉。没有这条，「男生，第一次约会，别太正式」会被当成「正式」。
3. **泛场合降权**：「周末去爬山」里的「周末」只是时间，不是场合。只有没有具体场合时，周末、休闲才当作场合；否则只给 +0.5 的平手分。

复用（不复制逻辑）：
- `parseConstraints`（`lib/adapt/offline.ts`）：预算数字、排除词、平底/舒适。建议顺手把其中的预算正则抽成 `rules.ts` 的 `parseBudget()`，两边共用。
- `parseSizes`（`lib/adapt/rules.ts`）：尺码，只透传给改编。
- `allowedGenders`（`lib/adapt/rules.ts`）：`allowedGenders("男装")` 正好返回 `["男装","中性"]`，可以直接当搭配性别过滤。

### 3.3 打分

对每套搭配打分，衣橱分取它最好的那一套：

| 信号 | 分值 | 作用 |
| --- | --- | --- |
| 像谁（命中主理人） | +5 | 直达那一间 |
| 具体场合命中 | +3，每多命中一个 +0.5 | 定位到那一套 |
| 风格命中 | +2，每多命中一个 +0.5 | 定位到那一间 |
| 泛场合（有具体场合时） | +0.5 | 平手时用 |
| 季节：说了夏天/热 | 四季的 6 套 +1 | 同时如实提示「这批衣橱以秋冬为主」 |
| 模糊预算词 | 对应 tier +1，相邻 tier +0.5 | 只在没有数字时 |
| 预算数字：总价 ≤ 预算 | +1，**超预算不扣分** | 排平手和写提示语，不做过滤 |
| 否定命中（avoid 出现在该套的场合或风格里） | −2 | 避开 |
| 性别 | 硬过滤 | 不跨性别 |

**为什么预算不做过滤**：改编可以把一套搭配压到很低。原型估算了每套的「可改编下限」：上装、下装（或连衣裙）、鞋这三类各换成本衣橱或同风格里最便宜的同类，结果 60 套的下限都在 ¥498–1,036 之间。也就是说，预算 ≥ ¥1,050 时几乎每一套都能改进预算。如果按预算过滤，「周末去爬山，1000 以内」会把真正对口的徒步搭配全部刷掉，换上一套不对场合的便宜搭配（原型第一版就是这样）。所以先选对的那套，再把预算交给改编。这个下限只是估计值，实际能改到多少以 `adaptOffline` 的结果为准，界面上不承诺具体金额。

**平手顺序**：分数 → 在预算内且总价更接近预算 → 首页衣橱顺序（与 M5 交错排序一致）。

**出结果**：第 1 名的衣橱和其中最好的那套，加上分数最高的另外 2 间做备选（不同衣橱）。

## 4. 等待与「流式」

### 4.1 时间线

| 时刻 | 发生什么 | 在哪儿算 |
| --- | --- | --- |
| 0 | 点发送或示例 chip：输入框收成引语标题，键盘收起 | 客户端 |
| < 16ms | 规则定位完成（60 套，纯函数） | 客户端 |
| ≈ 250ms | 等键盘收起（`visualViewport` resize，或 300ms 兜底）后开始转：灯光回亮，轮播转向推荐那间 | 客户端 |
| ≈ 0.9–1.4s | 停稳：理由行和备选 chip 浮起（`springs.rise`），读屏播报，`warmCloset` 预取这间衣橱页 | 客户端 |
| 与上同时 | 后台 `POST /api/locate`：句子 + 规则候选 id | 服务端 → Claude |
| ≈ 1.5–4s | AI 回来，按 §4.4 合并 | 客户端 |
| 4s | 超时：静默保留规则结果，不弹错误，也不标「规则模式」（D48） | — |

用户在 **0.25 秒看到画面开始动，1.2 秒拿到完整答案**。AI 永远不挡路。现在改编的 15 秒等待（FA-52）在这里不会出现。

### 4.2 规则放在客户端（推荐）

首页 `page.tsx` 在已有的 `getCurators()` 旁边并发取 `getOutfits()`，投影成索引随 `closets` 一起下发：`{id, curatorId, name, occasionTags, styleTags, season, budgetTier, total, gender}`，60 条约 11KB，gzip 后约 3KB。规则是纯函数，放 `lib/locate/`，客户端和服务端共用，服务端拿它校验 AI 的输出。

- 好处：没有网络往返，`/api/locate` 挂了也照样出结果；首页和目录本来就由同一次渲染拿数据，不新增失败点（FA-01 修好后两者同时可用）。
- 代价：首页多一次查询。FA-11 的 React `cache()` 落地后可以和搭配页共用。
- 备选是服务端算：页面更轻，但每次都要多一次往返，还多一次 Supabase 依赖。已按客户端定，见 §7 末尾。

### 4.3 AI 精排

- **输入**：用户原句 + 候选集。候选集 = 规则前 8 套 ∪ 每间衣橱分数最高的 1 套（去重，不超过 18 套，已按性别过滤）。每套带 `outfit_id、衣橱名、搭配名、场合、风格、总价、style_note`。规则分不出高下的审美词，比如「暖一点」「别太隆重」「显高」，靠 `style_note` 这段中文描述让 AI 判断，规则读不懂这段话。
- **输出**（structured outputs，沿用 `ai.ts` 的 `client.messages.parse` + `zodOutputFormat`）：`picks: [{outfit_id, reason ≤ 24 字}]`（1–3 个）+ `reply`（≤ 40 字，给用户的一句话）。
- **校验**：picks 必须是候选集里的 id，并且性别允许，否则整组丢弃，用规则结果。照 `adaptWithAi` 的「目录外 id 拒绝」处理，但不重试。
- **参数**：`timeout: 4000`（TS 单位是毫秒），`maxRetries: 0`（默认 2 次重试会让最坏耗时翻三倍）。`stop_reason === "refusal"` 时当失败处理。
- **模型**：默认沿用代码里现有的 `claude-opus-5-5`，`output_config.effort: "low"`（Opus 5.5 的默认是 medium，要显式写；思考关不掉，只能靠 effort 控制）。理由：规则已经保证了 1–2 秒内有反馈，AI 只是复核，4 秒以内回来就算赚到。上线后看超时率，若超过约 30%，再请用户决定要不要换 `claude-haiku-5-5`（延迟和成本都更低，效果待实测）。这里不替用户换模型，列入 §7 决策项 ②。
- **缓存**：Opus 5.5 / Haiku 5.5 的最小可缓存前缀是 512 token。只给候选集时系统提示约 400 token，达不到最小值，不缓存也够快。如果以后改成把 60 套全量放进系统提示（约 4–6k token），再加 `cache_control`。
- **延迟是估计**：现在改编要 15 秒，主要因为要输出 6 件单品的理由和摘要（`max_tokens` 16000）。定位只输出 1–3 个 id 和两句短话，预计明显更快，但**没有实测**，实施后第一件事就是在演示网络下测 p50 和 p90。

### 4.4 AI 结果怎么合并（不来回跳）

| 情况 | 处理 |
| --- | --- |
| AI 第 1 名与规则相同 | 理由行换成 AI 写的那句，交叉淡化 .35s；备选 chip 按 AI 顺序重排 |
| 同一间，换了另一套 | 只换理由行里的搭配名和价格 |
| 不同间，且用户停稳后还没碰过（没拖动、没点 chip、没点主按钮），并且距离停稳不到 2.5 秒 | **只再转一次**，理由行写「再看了一下，这间更合适：……」。这句话属实，因为 AI 确实复核过 |
| 不同间，但用户已经操作过，或已超过 2.5 秒 | 不动轮播，AI 首选放进第一枚备选 chip，前面加一个香槟色小点 |
| 超时、出错、拒绝 | 什么都不做 |

**不逐字流式**：输出只有一两句话加几个 id，逐字流出只会让理由行抖动，还要处理半截 JSON。「先给你一版，AI 再复核」的节奏已经由两段式本身给出，和审计 M1 搭配页即时草案是同一个模式。建议把这个「规则先出、AI 复核、差异合并」的小模块写成两处都能用的形状，M1 实施时直接复用。

## 5. 结果呈现与衔接

### 5.1 首页：轮播直接转过去

- 目标那间不在当前筛选结果里时（手机筛选在 Index 区），先清空筛选（整条淡入，已有逻辑），再转。
- 距离 ≤ 2 间：用 `springs.step`。距离 > 2 间：在 `lib/motion.ts` 新增一档更柔的 `springs.travel`（约 1.2 秒停稳），像镜头横移，不是快进。
- 转动过程中不挂载视频：加一个 `traveling` 标记，停稳后中央那间才开始播放。否则每经过一间都会挂一次 `SceneVideo`，拉一次视频请求。这件事和 FA-10(1)「视频挂载去抖」合并做。
- 环境光已有 220ms 防抖，停稳后才换，不用改。
- **把查询当滤镜**（完整版）：结果态下，用户滑到任何一间，理由行都显示「这间里最接近的一套」。分数已经全部算好，代价很小。最小版只在推荐的 3 间显示，其余各间回到原 tagline。

### 5.2 走进衣橱：共享元素过渡不动

- 主按钮仍是「走进衣橱」，`navigateWithHero` 一行不改。首页到衣橱页的签名时刻原样保留。
- 结果态下点理由行里的搭配名（文字链接），直接去 `/outfit/O31`。这是次要入口，不做成第二个主按钮。
- **句子不进 URL**：用户的话可能带尺码、身材、预算，URL 会被分享和记录。照 `sc-home-closet` 的做法存在 sessionStorage：`sc-locate = {q, query, closetId, lookId, at}`，30 分钟有效。URL 里只有已有的 `?c=C06`。

### 5.3 衣橱页：提示，不自动滚

- 衣橱页场景底部本来就有滚动提示 `.cue`（`href="#looks"`）。命中 `sc-locate.closetId` 时，文案换成「为你挑的「户外草坪婚礼」↓」，`href` 改成 `#look-O31`。
- 对应的搭配卡加 kicker `For you` 和一道 1px 香槟细线，不加扫光。规范里扫光专门表示「被换掉的单品」，不混用。
- **不自动滚动**：进场是 3 秒的虚焦推清晰，自动滚会打断审计认定的签名时刻。只给提示，滚不滚由用户决定。

### 5.4 搭配页：预填同一句话，不自动改编

- `Adapter` 挂载时读取 `sc-locate`；`lookId === outfit.id` 时把原句填进输入框，输入框上方加一行 kicker「接着你在首页说的」。
- 这套超预算时，输入框下方加一行如实的说明：「这套 ¥1,394，比你说的 800 多 ¥594；点「改编这一套」按这句改」。
- **不自动运行**：在 M1 即时草案落地前，改编还要等 15 秒，自动跑会把用户直接带进最长的等待；而且改不改应该由用户决定。M1 落地后可以改成自动出草案（完整版）。
- 衣橱 → 搭配的共享元素过渡（FA-19）和搭配页首屏改清晰封面卡（FA-51 方案 B）审计已放到截止后，本方案不依赖它们。完整版在这两项之后再接「首页理由行缩略图 → 搭配页封面」的过渡。
