## 1. 已确认目标与尚未成立的能力

用户希望形成以下闭环：

1. 创建者用照片、视频和语音向 Agent 描述衣橱，由 Agent 辅助生成并完善公共衣橱。
2. 浏览者通过文字或语音表达需求，选择服装与配饰，加入自己的试衣间。
3. 个人试衣间作为购物车的体验延伸，支持组合、比较、试穿与后续购买衔接。
4. 浏览者可上传本人照片／视频，让 AI 生成准确的个人 3D 形象，并获得一键试穿和实时体验。
5. 收藏达到未定阈值后，可选择付费私密个人衣橱，保存自己的选品与搭配。

“准确”“实时”“一键”是需要达成的体验目标，不是已经测得的技术属性。
身份相似、身体几何准确、可动画、衣服能套上、布料真实和合身判断必须分别验证。
一次生成的漂亮图片、演示视频或可旋转人形，不能证明以上所有目标成立。
完整愿景保留；建议分阶段验证不代表把愿景缩减成单张图片试穿。

| 模块 | 本轮完整需求 | 待决定与边界 |
|---|---|---|
| F10 建橱 Agent | 以照片／视频／语音形成公共衣橱草稿 | 审核、资产制作、权利与发布，不自动确认商品事实 |
| F11 个人试衣间 | 文字／语音选衣与配饰、组合、比较、移除 | 不是已付款订单或库存预留；试穿能力逐件判断 |
| F12 化身与试穿 | 本人形象、准确 3D、一键试穿、实时体验 | 数据条件、模型路线、精度、成本和时延均待验证 |
| F13 收藏与私密衣橱 | 收藏及可选付费私密个人空间 | 触发阈值、计数、价格、权益、续费及到期规则未定 |
| F14 数字权益 | 记录可访问或使用的数字内容权益 | 不默认授予实物所有权、版权、转售或训练权 |
| F15 归因分账 | 关联来源衣橱、推荐与真实交易结果 | 收藏／试穿不等于成交，不向创建者暴露个人身体数据 |

## 2. 公共衣橱与个人形象是两条不同路径

公共衣橱的五类入口来自用户要求：

- 明星及团队。
- 网红，尤其时尚穿搭博主及团队。
- 品牌主题衣橱；用户提到的设计师／秀场仅是意向例子，不是已有合作或资产授权。
- 特定风格主题，例如休闲、老钱、运动。
- 对穿搭有研究的个人申请创建，审核通过后上线。

五类是内容发现入口，可以组合；品牌、人物与风格不应被误建为互斥的主体类型。
公共衣橱可以是策展空间，不要求复刻实体房间、真实住宅或某个人完整拥有的衣物。

| 路径 | 可处理的内容 | 不能自动得出的结论 |
|---|---|---|
| 创建公共衣橱 | 有使用权的照片、视频、语音、商品与主题资料 | 创建者持有衣物、明星合作、未知背面、品牌与可售 SKU 均已核实 |
| 建立本人形象 | 用户自愿提交的本人资料及获授权的派生模型 | 可公开形象、供他人下载、广告使用或训练模型 |
| 收藏与私密衣橱 | 商品引用、搭配和用户选择保存的私密结果 | 获得原图版权、商品所有权或创建公开衣橱的资格 |

创建 Agent 的输出默认是草稿：场景、候选单品、文字、缺失资料和需要核实的声明分别呈现。
模型生成出的背面、内侧标签、Logo、材料与尺寸不能被写成商品事实。
人物关系继续区分本人原件、本人穿过、推荐、同款新品和相似风格，按证据审核。
创建者确认草稿不替代平台的发布权限与必要内容审核；是否具有直接发布权另行规定。
从私人选品另建公共策展内容时须创建独立副本、主动申请并审核素材使用权，不复制私密化身或身体资料，也不因付款或收藏自动公开。

## 3. 浏览者的完整体验建议

### 3.1 选衣与个人试衣间

普通浏览、搜索、详情、收藏与选品不应以先上传本人照片为条件。
建议允许访客先建立临时试衣间；跨设备长期保存是否需要账号由账户方案决定。

1. 用户可以输入“找适合通勤的外套和包”等诉求，也能主动开启一次语音输入。
2. 语音先转成可核对文字；涉及预算、颜色、尺码、商品指代不明时，先澄清或展示候选。
3. Agent 只从实际可访问的目录中推荐，区分已知资料、编辑判断和缺失信息。
4. 用户确认添加；“这件”“上一套”等指代应对应当前商品，不猜测并替换其他款。
5. 试衣间保存商品、变体、来源衣橱、数量、资产适配状态和价格库存时间。
6. 用户可增删单品、切换搭配和比较；重试同一添加操作不产生意外重复项。
7. 只有实际适配的模式显示可执行的试穿操作；不支持的服装说明原因并保留普通浏览。

麦克风按用户主动操作开启，提供录制状态、停止和文字替代，不默认持续监听。
浏览器麦克风许可不等于用户同意保存语音、建立身体形象或训练模型。
试衣间不是订单，不预留库存；转结算时重新核对价格、规格、库存、配送及责任主体。
生成造型中出现的替代鞋包、首饰或品牌，不能自动变成用户加入的商品。

### 3.2 自愿建立本人形象

进入需要本人资料的试穿模式时，再解释输入要求、用途、保存期和处理方。
用户选择继续后才发起上传或相机操作；拒绝后可以保留试衣间并浏览商品。

- 按实际路线提示拍摄条件：光照、视角、完整身体、遮挡、镜头与尺度参照，不默认任何照片都够用。
- 建议使用普通合适衣物，不以要求裸露或不必要的敏感身体影像作为服务入口。
- 检查模糊、多人、严重遮挡和缺少视角，给出可理解的补拍要求；不伪造隐藏几何。
- 若用户补充身高或围度，区分“用户填报”“图像估计”“独立实测”，保留不确定性。
- 生成后先让用户确认身份外观与明显身体偏差；确认“像我”不代表测量精度通过。
- 修正和重建生成新版本，不能把用户不同意的身体变形默认为真实个人特征。

不提供未经本人同意上传他人形象并克隆的入口；代表他人提交需有明确资格与相应产品规则。
人脸身份验证不是试穿的当然前置；不为追求“准确”默认引入额外的人脸身份数据库。

### 3.3 一键试穿与结果反馈

一键表示用户操作简洁，后台仍可能需要异步建模、排队、资产适配或渲染。
试穿前应核对形象版本、商品变体、组合和当前可用模式，结果绑定这些输入版本。
结果持续标明“2D 生成预览”“真实 3D 交互”或其他实际类型，以及已知范围和限制。
建议把“观察商品”和“本人试穿”作为可分辨的视图，前者保留原始服饰模型，后者使用当前授权的个人形象。
真实 3D 模式支持已验证的旋转和姿态；2D 结果只提供已有画面，不能把图片翻转当作真实侧背面。
多件搭配提供单品与层次清单，可移除、替换和回看规格；不能为隐藏穿模而自动改身形或换成相似衣服。
用户可举报“衣服不对／标识变化／颜色不对／身形失真／遮挡／穿模／尺码判断不可信”。
反馈不自动成为训练授权；修复前不能把结果错误写回商品资料或身体测量事实。
删除搭配、重试、换规格和返回时保留合理上下文；价格变化不靠旧预览静默成交。

## 4. 技术能力必须拆开验证

| 能力 | 所需条件与可能路线 | 可验证的结论 | 不能代证 |
|---|---|---|---|
| 身份外观相似 | 自愿提供的本人参考，外观重建／贴图等 | 在约定视角和条件下用户认可外观 | 精准身体围度、身份认证或真实衣物合身 |
| 身体几何与尺度 | 足够视角、尺度信息，必要时额外测量或深度 | 指定身体维度与独立参考的误差 | 单张无尺度照片能精确还原所有尺寸 |
| 可动画化身 | 可用几何、骨架、蒙皮、关节与姿态测试 | 支持列明姿态和动作，变形可接受 | 任意动作都自然、运动时测量仍准确 |
| 服装资产适配 | 服装模型、代表尺码、拓扑、绑定或碰撞准备 | 指定衣服可在指定化身／姿态上展示 | 普通可旋转 GLB 自动具备版片或真实布料 |
| 2D 生成试穿 | 本人图像和商品参考，生成模型与权限 | 特定视角的视觉搭配预览 | 真实 3D、背面事实、物理垂坠或尺寸合身 |
| 真实 3D 布料与 fit | 身体几何、服装版片／规格、材料参数、碰撞与仿真 | 指定条件下与实穿对照的一致性 | 手感、舒适、所有体型与所有动作均准确 |
| 已有化身实时交互 | 已生成且优化的资产、设备与渲染链路 | 指定设备上的旋转、换装响应与流畅度 | 上传后即时完成准确建模或实时布料计算 |
| 异步重建／生成 | 作业队列、处理服务、版本与恢复 | 在测得的时间和成本内产生相应结果 | 以最终图片流畅显示宣称端到端实时 |

身份相似和尺寸准确需要不同评价；身体表面估计受衣物、姿态、遮挡、镜头和尺度歧义影响。
用户填报身高可以辅助尺度，但不自动验证围度、比例或隐藏部位。
核心选中旋转服饰继续要求完整真实模型，约定的 GLB 资产路径不因试穿增加而被取消。
GLB 是资产容器与交付形式；“存在 GLB”不证明骨架、布料参数、全部尺码或 fit 能力。
2D 试穿可以作为独立模式研究，但不能替代真实 3D 化身、可旋转服饰和物理合身的验收。

## 5. 建议落地顺序与技术闸门

以下是验证顺序建议，尚未选择模型、供应商或实施栈，也不代表实验获准执行。

| 闸门 | 应准备的证据 | 通过后才可作出的有限声明 |
|---|---|---|
| G0 用途与处理条件 | 真实数据所需授权、处理方、成本、使用权、保存删除与测试计划 | 可以开展获批范围的数据试点，不是功能成功 |
| G1 采集可用 | 视角覆盖、清晰度、遮挡、人数、尺度和失败原因记录 | 此输入满足所选路线要求，不是任意输入都有效 |
| G2 外观重建 | 受许可样本、用户核对、指定视角对照与失败分类 | 在这些条件下外观达到选定标准，不等于测量合格 |
| G3 几何测量 | 独立实测参照、单位、重复测量、误差分布和适用人群条件 | 只有已测维度在已测条件下的精度结论 |
| G4 可动画与配饰 | 骨架、蒙皮、姿态、连接点与遮挡测试 | 支持列明动作和配饰，不扩展到所有姿态 |
| G5 服装适配 | 服装与变体映射、尺码、层次、碰撞及素材审核 | 指定服装可按列明模式试穿，不证明物理合身 |
| G6 2D 预览 | 服装保真、人物保真、颜色标识、细节变化与用户理解 | 明示的生成搭配预览，不是 3D 或尺寸保证 |
| G7 真实 3D／fit | 实穿对照、版片规格、材料、身体与动作条件、偏差和失败率 | 对已测对象及任务的有限 fit 结果，不是普遍保证 |
| G8 交互与运营 | 设备网络、排队与端到端时延、帧时间、成本、失败重试及删除证据 | 只对测得范围说明实时体验与可持续性 |

建议先明确商品与试衣间身份、权限和作业边界，再用小规模自愿样本逐条比较路线。
没有身体精度证据时，可以研究外观形象；没有 fit 证据时，只展示清楚标识的视觉结果。
这类中间成果不得对外称为用户所要求的准确实时 3D 试穿已经完成。
真实试点需另获实施和数据处理授权；本轮只完成规范，没有运行上述实验。

## 6. 非标准姿态、配饰与多件叠穿

- 姿态：分别测试站立、转身、坐姿、抬臂及所声称支持的动作；非标准姿态不能套用站立结论。
- 遮挡：长发、手臂、原有衣物、包带和多人背景影响重建时，提示补拍或缩小支持范围。
- 配饰：鞋、包、帽子、眼镜、耳饰与首饰需要不同定位与尺度，不能用上衣适配证明配饰准确。
- 鞋履：脚部尺度、鞋楦、左右脚与姿态单独处理；外观贴合不证明尺码或舒适度。
- 叠穿：内外层顺序、厚度、开合与碰撞逐组合检查，不能把单件成功扩成任意多件组合。
- 场景：头发、身体和衣服的前后遮挡应合理；无可靠支持时不能“画掉”身体或改衣服来隐藏错误。
- 动态：换装后动作中的穿模、抖动、漂移和配饰脱离分别记录，不只截一张最好看的正面图。
- 变体：切换尺码与颜色必须保留真实映射；模型只代表一个尺码时不得通过任意缩放声称适合所有尺码。

每件商品记录支持模式、体型／姿态条件、配饰连接点、已测叠穿组合和已知冲突。
不支持时保留试衣间与商品信息，明确“该组合暂不支持”，而非生成任意相似衣物代替。
用户选择不展示身体某部位或删除参考图时，结果有效范围与是否需要重新授权应可解释。

## 7. 准确度、实时性与用户验证数据

各项阈值应在实验前确定；以下是测量口径，不是已获得的数值。

| 维度 | 建议记录内容 |
|---|---|
| 身份相似 | 用户与独立评审对规定视角的评价、明显外观变形、拒绝率与原因 |
| 几何精度 | 各测量部位绝对误差、分位数、重复性、尺度来源、适用与失败条件 |
| 服装保真 | 款式、长度、颜色、Logo、花纹、配件、缺陷等变化率及误导案例 |
| 3D 稳定 | 正侧背、动作、遮挡、层次、穿模、漂移和恢复，不只评单帧 |
| fit 有效性 | 在自愿且获准的实穿对照下，对声明任务的符合程度、误导和不确定结果 |
| 时延 | 上传、校验、排队、重建、适配、渲染、下载各段与端到端分位数 |
| 实时交互 | 具体设备网络、资产、帧时间、输入到可见响应，远程串流还需计传输时延 |
| 覆盖与公平性 | 在必要且获授权的样本条件中报告覆盖、分组误差与失败，不把平均值推及未测群体 |
| 运营成本 | 每类作业成本、失败与重试成本、排队容量、超时和可用率 |
| 用户理解 | 用户能否分清生成预览／真实 3D／合身结果，是否错误理解即时性或精准尺寸 |

记录数据集来源、许可、样本条件、版本、样本量、协议和真实失败案例，不只挑选成功演示。
训练集表现、供应商营销图、论文指标或他人设备结果都不能直接作为本平台达标证据。
“准确”必须指明对象和条件；“实时”须区分已生成形象的交互、重建耗时和布料更新。
尺寸建议即使未来可用，也需单独验证，不因用户认可形象相似就推荐确定尺码。

## 8. 本人媒体与身体数据的产品化处理

### 8.1 上传前按用途说明并选择

授权应在相应动作前呈现，不能把照片、声音、身体估计、公共发布和训练混在一次同意里。

| 数据与用途 | 上传前需说明的内容 | 用户选择 |
|---|---|---|
| 语音选衣／创建草稿 | 转写处理方、原音与文字是否保存、用途与保存期 | 只在主动录制时处理，可用文字替代 |
| 本人照片／视频 | 用于哪种形象或试穿路线、必要视角、处理方和保存期 | 拒绝不影响普通浏览与选品 |
| 身体估计与测量 | 哪些数据由填报／估计／测量而来，使用目的、误差与保存期 | 不默认用于广告、画像或其他目的 |
| 化身与试穿派生物 | 生成哪些模型／贴图／图像，私密范围、保存与删除关系 | 可选择是否长期保存，不自动公开 |
| 公共策展独立副本 | 有权公开的商品／场景内容、副本范围、审核及发布后撤回限制 | 主动申请并单独审核，不复用建模同意或包含私密化身与身体资料 |

原始视频的音轨若不是所选用途所必需，应避免处理或按已说明规则移除。
不能为了 2D 外观预览额外默认收集不必要的完整身体测量或长期保存原始视频。
可选用途与核心功能分开；收回可选用途不应删除用户未要求删除的商品收藏。

### 8.2 保存、第三方与默认不训练

- 原图、原视频、抽帧、裁剪、转写、身体测量、特征表示、化身、贴图、预览分别列保存期。
- 建议只保留完成所选功能所需的最短时间；选择保存形象不等于选择保存全部原始视频。
- 实际天数、到期动作、备份清理周期及处理地区须在真实数据试点前确定并披露，不能无限期“待定保存”。
- 2026-10-16 已确认（D47）：3D 形象用的原始照片在形象生成完成 30 天后自动删除，3D 形象保留到用户删除，可一键全删；备份清理周期与处理地区仍待确定。比赛版的执行方式见 §12.7：到期清理由 `npm run avatar:purge` 与打开页面时的惰性清理完成，每日定时任务尚未配置。
- 默认不将用户媒体、身体信息或派生形象用于训练；未来若考虑训练，需独立可选授权和另行评审。
- 接入外部处理方前核实合同、保留政策、训练用途、子处理方、删除能力和实际数据流。
- 若处理方不能满足已承诺的不训练、保存或删除条件，不可只靠前台文案接入真实用户数据。
- 供应商不等于已获授权合作；本轮未选择服务商，也没有验证任何外部方已满足这些条件。

### 8.3 私密访问与数据流

- 消费者私密衣橱、本人媒体、身体数据、化身和试穿结果在本版仅本人可见，不提供分享、邀请或团队访问入口。
- 创建者、创建者团队和商家不继承消费者私域访问权；公共衣橱角色与私域权限分别校验。
- 公开衣橱与私人试衣间的数据、搜索索引、访问地址和缓存范围分别处理，不靠“链接难猜”保证私密。
- 工作人员访问需有处理理由、最小范围与记录；日志只保留必要状态，不写入原始身体媒体或可复用访问令牌。
- 缩略图、下载地址、导出包和生成任务同样校验归属，跨账号不可访问。
- F15 归因仅使用必要的商品、来源、事件和真实交易标识，不传用户照片、身体尺寸或私密搭配内容给创建者。
- 若用户申请创建公共策展内容，须另建独立副本、选择有权公开的商品／场景资料并经审核；不得直接分享私密衣橱或把私密化身、身体媒体纳入副本。
- 公共副本发布前展示内容与范围，撤回后停用平台可控链接与缓存；不保证收回公众已下载的副本，也不使原私域内容变为公开。

### 8.4 撤回、删除与下游派生物

用户应能查看保存内容、停止新处理、撤回相关用途并请求删除，不以付费作为删除前提。
操作前说明受影响对象、版本和派生范围；“清原视频”不等于“撤回建模用途”或“删除全部”。

| 操作 | 删除及停止范围 | 可以保留的内容 |
|---|---|---|
| 仅清理原始媒体 | 所选原图／视频及相关原始抽帧、裁剪等中间副本，停止继续读取这些文件 | 用户主动保留、具有独立有效授权且仍在保存期内的化身／结果；普通商品收藏不受影响 |
| 删除一次试穿结果 | 指定结果版本及其缩略图、缓存等副本，停止该结果的后续展示与自动重试 | 本人化身、其他获准结果和选品；不自动清空整个试衣间 |
| 删除某个化身版本 | 停止引用该版本的任务，清理该版本及依赖它的关联试穿结果 | 另有有效授权且独立存在的其他版本、普通商品收藏；保留项在确认前明确 |
| 撤回对应处理目的 | 停止该目的的新任务，清理该用途涵盖的媒体、身体资料、特征表示、化身和关联派生版本 | 其他独立有效用途的必要内容及普通收藏；不能用原授权继续相关处理 |
| 删除全部个人形象资料 | 清理全部相关原始、中间、身体、化身及试穿资料并停止相关任务 | 必要订单记录另按规则最小化保留，不保留人体影像 |

对上述操作覆盖的未开始任务停止执行，运行中尽力取消；撤回用途或删除版本后的迟到结果不得重新显示或恢复访问。
清理原媒体后，仍获准保留的化身可以在原用途和保存期内使用，但不能从已删输入恢复原图或恢复已停止的重建任务。
按所选范围向实际外部处理方发送删除请求，清除可控缓存，记录下游确认及备份到期清理状态；不把备份恢复为重新可见内容。
用户可见“已停止使用／删除处理中／已完成可控范围删除”，不能把发出请求冒充全部物理副本已消除。
依法必须保留的必要订单／交易记录与本人媒体分开，并说明例外范围，不因留存订单而保留照片、身体视频或人体形象。
取消可能已产生计算成本，是否收费或退费必须事先说明，不承诺所有取消都会退还成本。

### 8.5 未成年人及第三方影像

普通衣橱浏览与选品不应被无必要的身体资料收集阻断。
建议真人身体建模试点先限制为符合所选市场规则的成年本人；这属于待确认的试点策略。
若允许未成年人，须先明确适用年龄、监护人授权、必要资料、保存与删除和支持范围。
未确定上述规则前不开放未成年人身体媒体处理试点；不把上传身份证件默认设为所有人的必要步骤。
多人视频、他人面孔或未经同意的影像应拒绝、重选或按可验证规则裁剪，不默认处理旁人形象。

## 9. 作业状态、取消与异常

形象生成、试穿和创建草稿需有独立作业身份、输入版本、授权版本和可恢复状态。
建议状态为：待校验、需补充、排队、处理中、成功、失败、取消中、已取消、已过期／已撤回。
具体接口、幂等、外部服务与存储责任见[实现架构与功能映射](实现架构与功能映射.md)。

| 情况 | 应有的产品行为 |
|---|---|
| 未授权或拒绝上传 | 回到试衣间继续选品，不重复强迫授权或自动开启相机 |
| 模糊／遮挡／非标准姿态 | 指明不足与可选补拍，不编造身体或隐瞒可靠性下降 |
| 无适配模型／不支持组合 | 保留选品与普通详情，说明当前模式不可用，不用相似款替代 |
| 排队／慢作业 | 明示异步状态、可离开与恢复；无可信进度不报假百分比 |
| 超时但结果未知 | 查询原任务，重试幂等，不让连续点击产生多笔不明费用 |
| 用户取消 | 停止后续使用与展示；运行中任务尽力取消，说明费用规则 |
| 结果失真或不满意 | 提供纠错、删除与重试入口，不把用户反馈写成已测尺寸事实 |
| 输入／授权已撤回 | 拦截迟到结果并处理相关派生物，不能用重试重新启用授权 |
| 设备不支持真实 3D | 可查看明确标识的静态结果或普通详情，但不计真实 3D 达标 |
| 账号或分享访问异常 | 失败关闭私密访问，给本人可恢复入口，不泄露他人的模型或结果 |

任务成功不自动发布公共衣橱、不自动收藏全部结果、不自动选定尺码或提交订单。
语音、2D 生成、化身重建和物理仿真的作业类型与费用应可分辨，不统称一个“AI 已完成”。

## 11. 候选验收与决策清单

以下是未来计划，不是当前已通过的功能或隐私测试。

1. 五类公共衣橱可以表达策展关系，创建草稿与审核发布分开，不假设实体房间或明星合作。
2. 创建 Agent 无依据时保留未知，不把生成背面、品牌、所有权与 SKU 写成已核实事实。
3. 普通浏览与选品不要求照片视频；语音可停止并有文字替代，歧义选择可核对。
4. 服饰与配饰进入试衣间后身份、规格、来源和状态正确；重试不会意外重复或成交。
5. 结果显示具体模式与输入版本，2D 不冒充 3D，异步不冒充即时建模，旋转模型不冒充 fit。
6. 纳入核心旋转体验的服饰有完整真实模型，图片与 2D 试穿不替代原目标。
7. 外观、几何、可动画、服装适配、物理 fit 与实时性有独立协议、阈值、证据及失败范围。
8. 非标准姿态、头发包带遮挡、多件叠穿与配饰均按实际支持范围提示，不自动换成相似物。
9. 授权逐用途、原始与派生保存期可查、默认不训练，实际下游条件与前台承诺一致。
10. 私域无分享／邀请入口；公共独立副本不继承私域权限，跨账号、私密搜索、缩略图、导出和任务结果均按归属控制。
11. 撤回能阻止新作业及迟到结果，删除覆盖派生物与可控下游，备份与例外状态如实呈现。
12. 用户可反馈失真、纠错、删除和重建；认可身份相似不自动被记录为身体精度通过。
13. 收藏阈值与付费规则明确且主动选择，到期不公开，删除不被付费门槛阻挡。
14. F14 权益不扩大个人资料使用权，F15 不把试穿当成交，不把身体资料传给分账参与方。

实施前必须收敛：目标人群与市场、试点年龄、准确度对象与阈值、采集方法、适配商品和姿态范围。
同时确定：模型与服务商许可、真实数据用途与保存期、下游删除、成本时延、收藏计数和付费权益。
长远目标全部保留，首个实施范围仍需明确批准；文档完成不代表具备准确、实时、一键试穿能力。

## 12. 多照片高还原 3D 形象路线（2026-10-16 补充）

### 12.1 需求与状态

- **已确认目标**（[决策记录](决策记录.md) D45、D46）：用户登录后可建立完整个人档案；上传多张本人照片，在 AI 协助下生成完整、精准、还原度非常高的本人 3D 形象。
- **已确认存储规则**（D47）：照片与 3D 形象存发起用户 Supabase 项目的私有桶，按用户隔离；只有发起用户提供 key 且用户单独勾选同意后，才发送给第三方生成服务；原始照片在对应形象生成完成 30 天后自动删除；3D 形象保留到用户删除；可随时一键全删。
- **建议**：下文选型与比赛版范围来自 2026-10-16 的服务调研，未经用户逐项确认，各服务条款中标“待核实”的内容未核实。
- **未验证**：本仓库没有用任何真人照片跑过生成，也没有任何服务的人体还原度、耗时或成功率实测数据。

“还原度非常高”是目标。比赛版不能把它写成已达成；对外表述按 D46：**“AI 根据你的多张照片生成可 360° 旋转的 3D 形象预览（还原外观轮廓，不代表精确本人或尺寸）”**。

### 12.5 与现有数据表的对齐（待对齐项）

`771a783` 已提交 `profile`、`avatar_photo`、`avatar_job` 三张表。与调研结论有两处要在实现时对齐：

1. **视角槽位（已定，2026-10-16）**：`avatar_photo.slot` 仍为 `front | side | back | face | extra`，不走迁移；上传只开放 front、side、back。适配器固定 `side` → left、`back` → back，不采集也不发送 right；真实服务要求正面 + 侧面、背面可选。决定记录在[实现架构](实现架构与功能映射.md) ARC-F41/F42 与 §14.1“视角映射”。
2. **作业状态**：`avatar_job.status` 为 `draft | queued | processing | succeeded | failed | canceled`，比赛版按此执行；§9 中的“需补充、取消中、已过期／已撤回”留到 v1。

### 12.6 上线前（接入真实用户照片前）必须满足的数据处理条件

以下条件未满足时，只允许用合成图开发，不得对真实用户开放第三方生成：

1. **第三方处理**：同意卡逐服务列出名称、发送内容（哪几张照片）、用途和对方保留政策，用户单独勾选（D47）。没有 key 或未勾选时不向外发送任何照片。
2. **fal 的输入留存**：fal 默认存储请求的输入与输出，且输入的 CDN 文件不会被删除。因此必须做到：不把照片上传到 fal 自带存储；只传自有私有桶生成的短时签名 URL；请求头加 `X-Fal-Store-IO: 0`；生成完成后通过 Platform API 删除可删的 payload 与输出。fal 侧是否仍有不可删副本、Tripo 条款是否适用，属于上线阻塞项，待核实。比赛版代码已按这几条实现（见 §12.7），但没有 key，从未实际调用。
3. **Meshy 备选**：非 Enterprise 资产保留最多 3 天且未见提前删除端点，训练用途未核实。这与 D47 的“一键全删”有冲突，核实前不得对真实用户启用该适配器。
4. **保留与删除**：原始照片在形象生成完成 30 天后自动删除；3D 形象保留到用户删除；一键全删清理数据库记录、私有桶文件、预览图和可控缓存，并对已发送过的第三方发出删除请求、记录回执状态（D47）。比赛版已实现清理脚本与删除请求记录，每日定时任务尚未配置（见 §12.7）。
5. **默认不训练**：不把用户照片、身体数据或派生形象用于训练；优先选择承诺不训练、可删除的服务。服务商条款不满足时，不能只靠前台文案接入。
6. **未成年人**：D47 未覆盖。建议真实试点只对成年本人开放，年龄门槛与监护规则由发起用户另行确认；确认前不处理未成年人身体照片。
7. **他人影像**：多人照片、他人面孔应拒绝或要求重拍；不提供替他人建模的入口。
8. **密钥**：`FAL_KEY` 等只放 `app/.env.local` 或环境变量，不进仓库、日志与客户端代码。

### 12.8 数字分身的脸部还原度：衡量方法与脸部精修（2026-10-23，D69）

2026-10-17 起（[决策记录](决策记录.md) D63）比赛版不做 3D：用户上传 2–5 张照片，生成正面、四分之三侧面、背面三张照片级标准形象照，正面同时是试穿底图。本节记录如何衡量“脸像不像”，以及据此加的一步脸部精修。实现细节见 `app/README.md`「数字分身」。

**衡量方法（可复现，不靠主观印象）**

| 项目 | 做法 |
| --- | --- |
| 模型 | OpenCV Zoo 的 YuNet（人脸检测，MIT）与 SFace（人脸识别，Apache-2.0）；FaceNet（facenet-pytorch，MIT）只作交叉验证 |
| 指标 | cos：生成图里的脸与本人参考正脸的余弦相似度。rank-1 与 margin：本人参考的 cos 减去最像的另一位同性别人物的 cos，大于 0 说明在测试集里能认出是谁。另报脸框像素高度，侧面只看是否检出，背面不评估 |
| 对照 | “本人另一张照片”（参考正脸 vs 本人全身或半身照里的脸）作为上限参考；“不同人”为同性别、其他虚构人物的参考正脸 |
| 素材 | 只用 AI 生成的虚构人物：3 位女性（正脸、侧脸、全身正面、全身侧面）与 f01、m01（`app/public/demo/models/`），另加 9 张虚构主理人头像作“不同人”对照。照片与结果放在仓库外 |
| 工具 | `app/scripts/twin-eval-gen.ts`（用线上同一套提示词生成，逐笔记账、设花费上限）、`app/scripts/face-eval.py`（打分） |

校准：SFace 下“本人另一张照片” cos 均值 0.681、rank-1 7/7；同性别不同人 cos 均值 0.458、最高 0.657。FaceNet 在这组人上连“本人另一张照片”也只有 6/7 认得出，区分度弱，只作参考。

**结果（每位人物 2 次，正面 n=10）**

| 方案 | 脸框高 | SFace cos | margin | rank-1 | FaceNet margin |
| --- | --- | --- | --- | --- | --- |
| 现状：2K 全身图 | 约 250px | 0.611 | +0.134 | 9/10 | +0.045 |
| 诊断：同样参考出半身特写 | 约 670px | 0.661 | +0.199 | 10/10 | +0.084 |
| 输出改 4K | 约 500px | 0.620 | +0.126 | 9/10 | +0.049 |
| 采用：正面脸部精修 | 约 250px | 0.665 | +0.159 | 10/10 | +0.042 |

结论：模型在脸大时能还原本人，在全身图里把五官画成“通用脸”；单纯提高分辨率没有用，身份在构图阶段就定了。脸部精修把头部放大后只重画五官再贴回，SFace 下与本人的相似度接近“本人另一张照片”，10 张中有 2 张因模型改动了构图而保留原图。

**仍未解决**

- 本轮没有人工评分，是否达到用户说的约 90% 主观相似度，需要按工作站 T6 的方式用这批虚构人物并排打分确认。
- FaceNet 交叉验证没有看到同样幅度的提升；配对来看，精修后与本人参考的相似度 8 张里 7 张上升，与他人的区分度 5 张上升。
- 全身图把脸型画窄的情况（测试人物 w03）精修帮助有限：为避免接缝，精修保留原头部轮廓。允许修正脸型宽窄的提示词试过，没有更好。
- 侧面（四分之三侧）用同一方法评估过（2026-10-23，10 张）：SFace 持平（cos 0.592 → 0.595），并排看 2 张更不像（被画老、转得更侧）、2 张略好、其余几乎没变，模型还常把远侧下颌画窄，所以不启用。背面不做。试穿只用正面，不受影响。
- 每个分身多约 0.15 美元、约 25 秒（本机 n=1）；Vercel 上的耗时未测。
